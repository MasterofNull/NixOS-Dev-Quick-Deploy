## Findings

**1. MEDIUM — §2.1 promises a "detectable conflict" for cross-identity reuse, but §3.1 step 2 / §3.2 `resolve()` never define that branch, and the `resolve()` table has no "journal-absent-for-this-entry_id" row.**
Section: §2.1, §3.1 step 2, §3.2 (the state table).
Scenario: the owner signs two distinct valid bump docs sharing the SAME `request_id` but a DIFFERENT `idempotency_key` (both are owner-signed, so `verify_bump` passes; the whole doc is signed, so a mutated `idempotency_key` is still a validly signed distinct doc). The second call's `entry_id = sha256(request_id ␀ new_key)` differs from the original's `entry_id = sha256(request_id ␀ old_key)`. At §3.1 step 2 the `by-request-id/<H(request_id)>` `O_EXCL` create returns `EEXIST` (the original holds it), so the call "hands off to `resolve(entry_id)`" — but `journal/<new entry_id>` does **not** exist, and §3.2's table has rows only for `committed`/`intent`/`aborted`, none for an absent journal. The behavior is therefore undefined: either `resolve()` faults on the absent journal (breaking `apply_bump`'s documented total-function/never-raise contract), or it resolves the *stored* original `entry_id` and returns the original's receipt — which is exactly the "silently-admitted second entry" outcome §2.1 claims the two-index shape prevents. This is a live `apply_bump`-path completeness gap, NOT a crash-recovery interleaving: it cannot double-bump or lose exactly-once at the epoch level (the CAS only fires on the fresh both-indexes-created path), so it does not defeat cases a/b/c/d. But rev5 Finding 4's own text lists "both independent uniqueness" as under-specified, and C6d's `closes_finding` claims to close all of Finding 4, so this unfulfilled stated guarantee makes the closure claim overstated and leaves an internal contradiction between §2.1's promise and the §3.2 algorithm.
Required fix (small, in-scope, no scope expansion): add to §3.2 (a) a "journal absent for this `entry_id`" row and (b) a cross-identity branch — on an index `EEXIST`, read the stored `entry_id`, compare the pointed-at entry's stored `request_id`/`idempotency_key` to the presented pair; an exact match is the replay/recovery path already specified, a mismatch is a typed deny (e.g. `DENY_IDENTITY_CONFLICT`), never a silent admit and never a fault. The mechanism already exists in the design (indexes store `entry_id`; the entry stores both ids) — only the resolution branch is missing. Add a crash/conflict vector to the §5 matrix and the §6 probe.
