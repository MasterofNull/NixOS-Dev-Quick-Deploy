## Findings

**Finding 1 (MEDIUM) — `audit_pending` is not durably persisted, and no reconciliation ("audit reconciled") ever runs, contradicting design §5 vector h.**
`scripts/ai/lib/revocation_epoch.py:1163-1186`. Design §5's vector-h row states: "after phase-commit, before projection | `committed`, epoch `new` | §3.2 return committed; **audit reconciled** | receipt returned; **`audit_pending` cleared**". For there to be something to "clear" or "reconcile," the committed journal entry must persist that a transaction is `audit_pending`, and `recover()`/`resolve()` must attempt to re-run the audit append and update it on success. Neither exists: `committed_entry` (the durable journal row) never carries `audit_pending` at all, and `resolve()`'s `committed` branch (`revocation_epoch.py:829-831`) and `recover()`'s per-entry loop (`revocation_epoch.py:930-940`) never touch `_append_audit_receipt`. **Concrete failure scenario:** the audit disk fills momentarily during a bump; the live caller is correctly told `audit_pending=true`; the process later restarts (or the identical request is replayed) — `recover()`/`resolve()` reconstructs the receipt and unconditionally reports `audit_pending=false`, permanently masking that the audit trail was never written for that specific bump, with no code path that will ever go back and write it. This does **not** cause a double-bump or violate the epoch's exactly-once guarantee (verified — old/new epoch in the reconstructed receipt is always correct), but it is a real, confirmed observability/audit-integrity regression relative to the frozen design's own stated behavior for this vector.

**Finding 2 (MEDIUM, coupled to Finding 1) — vector h has no dedicated test, and the live-path mirror of Finding-4-case-2 is untested.**
`scripts/testing/test-revocation-epoch.py` ships `test_vector_{a,b,c,d,g,i,j}` plus two extra probes, but no `test_vector_h_*`. The file's own header comment (lines 152-159) argues e/f reduce to d/g by `os.replace` atomicity — a reasonable equivalence-class argument I verified holds (same `resolve()` branches, same on-disk read-epoch outcome) — but h starts from a **different** on-disk phase (`committed`, not `intent`) and is specifically about the audit-reconciliation action the design calls out by name; it is not reducible to g's assertions the way e/f are to d/g. Design §8 freeze criterion 4 requires "each of the a–i crash vectors yields exactly-once idempotent receipt or a typed `quarantined`... all proven by the extended test-revocation-epoch.py" — h is not proven, and per Finding 1, had it been tested against the design's literal expected outcome, it would have failed. Separately, the live-path branch that rolls back a just-created index after the *second* index's `EEXIST` (`revocation_epoch.py:1090-1101`, Finding 4 case 2 on the live path, as opposed to via `recover()`) is also unexercised by the shipped suite — I confirmed it is in fact correct (see Assessment §2), so this half of the finding is coverage-only, not a functional defect.

**Finding 3 (LOW, informational) — `sd_notify(READY=1)` fires before `bind()`/`listen()`, not after.**
`scripts/ai/lib/revocation_epoch_transport.py` `__main__`: `_sd_notify_ready()` is called immediately after `recover()` returns, **before** `serve(_sp, build_env_handler())` — and `serve()` (lines 128-158 of the same file) is what actually calls `srv.bind(socket_path)` and `srv.listen(16)`. So systemd may observe "active (running)" (and, once this unit is ever enabled, allow any `After=`/`Requires=` dependent to proceed) for a brief window before the AF_UNIX socket path even exists on disk. This does **not** weaken the recover-before-listen data-consistency guarantee under review — `accept()` cannot literally happen before `listen()` regardless of when `sd_notify` fires, so no request is ever served against an unreconciled journal — and it is arguably compliant with the design's own literal wording ("readiness... is emitted only after `recover()` returns," which does not explicitly pin it to after `listen()`). Verified on this system's systemd (260) that `NotifyAccess` is implicitly set to `main` when `Type=notify` is used without an explicit `NotifyAccess=` (confirmed via `man systemd.service`), so the earlier hypothesis that the missing `NotifyAccess=` line would break startup is **incorrect and retracted** — the Nix wiring for `Type=notify` is functionally fine as written. Recommend, but do not require, moving `_sd_notify_ready()` to after `serve()`'s `listen()` call in a later slice, for strict systemd-notify-protocol correctness once this authority is actually enabled.

**Finding 4 (LOW, informational, pre-existing pattern) — a live (non-crash) `OSError` raised after `os.replace()` has already durably applied can return a deny for a mutation that actually succeeded.**
If `_write_epoch_atomic`'s or `_atomic_rewrite_journal_entry`'s final directory-`fsync` raises *after* `os.replace()` has already renamed the file into place, `apply_bump` (via its inner `except OSError` at line ~1160, or the outer `except Exception` at the function's end) returns `DENY_EPOCH_WRITE_FAILED`/`DENY_INTERNAL` to that caller even though the epoch/journal state already reflects the mutation. This is not new to C6d (the same class of exception existed against the old ledger-write pair) and is self-healing: a client retry of the identical request lands on the `resolve()` `intent`+`current==new_epoch` (g) or `committed` branch and gets the correct answer, and `recover()` on a later restart reconciles it the same way. Not a double-bump or a permanent wedge; flagged only for completeness since it is a caller-visible "denied but actually happened" edge case outside the a-i crash-injection framing (it requires a live caught exception, not a process crash).

## Explicit verdicts

1. **Design-faithful:** Mostly yes — the journal + two-index primitive, the identity gate, the `resolve()` phase table, the `recover()` three-step bipartite reconciliation, and the `aborted→intent` tombstone reuse all match the frozen design's §2/§3 text exactly, file:line verified. **Gap:** vector h's audit-reconciliation semantics (Finding 1) are not implemented.
2. **Exactly-once across crash vectors:** **Yes**, for the epoch/receipt guarantee itself. Verified live for a, b, c, d, g, i, j plus the reverse-direction case-2 mirror I added; no double-bump, no permanent wedge, no lost-forever bump found in any interleaving traced or executed. The audit_pending gap (Finding 1) does not compromise epoch exactly-once — only the auxiliary audit-pending flag's fidelity across a restart/replay boundary.
3. **Interpretation-#5 safety:** **Yes.** Confirmed live: a replay of an already-`committed` transaction returns the identical reconstructed receipt (`ok=True`, same old/new epoch) with no second epoch mutation; `DENY_IDENTITY_CONFLICT` fires correctly for both directions of same-request-id/different-idempotency-key and same-idempotency-key/different-request-id reuse (the design only names the former; I verified the latter too); `DENY_RETRY` fires for journal-absent-orphan-index and for journal-present-but-uncommitted-`aborted` on the live path, never `DENY_REPLAY` (which is now retired from the gating path, kept only for import compatibility).
4. **Recover-before-listen:** **Yes**, in-process ordering is correct and unconditional (`recover()` always runs to completion under `epoch.lock` before `serve()`/`bind()`/`listen()`/`accept()`, gated on no time/flag condition). Finding 3 is a readiness-signal timing nitpick, not a violation of this barrier.
5. **`enable=false`/no-activation:** **Yes**, confirmed unchanged — only `Type` flips `simple`→`notify` inside `serviceConfig`; `enable`, hardening lines (`NoNewPrivileges`, `ProtectSystem="strict"`, `ProtectHome="read-only"`, `RestrictAddressFamilies=["AF_UNIX"]`, `CapabilityBoundingSet=""`), socket path, and control-socket confinement are all byte-identical to main. `NotifyAccess` omission is a non-issue on this systemd (implicit `main`), verified via `man systemd.service`.
6. **Tests real:** **Yes.** Ran the actual suite in an isolated scratch tree: `113 passed, 0 failed`, matching the handback's claimed count. Crash vectors inject genuine on-disk journal/index state, not fixtures. Coverage gaps: vector h (Finding 2) and the live-path mirror of case 2 (Finding 2, functionally verified correct by me, but unproven by the shipped suite).
