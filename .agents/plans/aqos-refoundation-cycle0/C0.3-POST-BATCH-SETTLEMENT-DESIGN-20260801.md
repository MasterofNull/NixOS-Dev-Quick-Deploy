## Objective

Settle C0.3 consumption truth after the unauthorized batch boundary without
rewriting history or editing the historical record. This design supersedes the
2026-07-30 Stage-2 authorization only for future settlement mechanics; it does
not invalidate or mutate preserved evidence.

## Prerequisites

All must be true before a recovery authorization can be activated:

1. AQ-OS progress-tracker parity has independent PASS, is committed and
   deployed, and its live dashboard plus integration `aq-qa` check are green.
2. `C0.3-BATCH-INTEGRATION-INCIDENT-20260801.md` receives independent exact-byte
   review.
3. The historical record, implementation acceptance, batch commit/parent, both
   protected tag objects/targets/content hashes, and non-ancestry checks match
   their frozen values.
4. The worktree may contain unrelated owner bytes, but the index is empty at
   authorization freeze and can later contain exactly one new settlement path.

## Additive settlement subject

The future implementation may create exactly one new file:

`.agents/plans/aqos-refoundation-cycle0/C0.3-POST-BATCH-SETTLEMENT-RECORD.md`

It must bind the incident, the tracker live-green evidence, the historical
implementation acceptance, the exact batch commit and parent, the historical
record blob/file hash, and the protected refs. It must permanently disclose
that the original one-file settlement procedure was bypassed.

The new record may recognize the parent authorization as consumed only through
the combination of the historical implementation and newly validated evidence.
It must not claim that the old Stage-2 authorization was activated, that the
140-path batch was an authorized settlement commit, or that evidence existed
before its actual timestamp.

## Fresh authority and separation

A new current-HEAD, hash-bound, single-use authorization is required. It must
name a bounded implementer and a distinct independent reviewer; freeze the
one-new-file ceiling; bind the clean index disposition and all prerequisite
hashes; and stop on any drift. The old Stage-2 authority is retired and cannot
be activated or replayed.

The implementer cannot accept its own record. A final exact-byte PASS must
precede staging. Only the orchestrator may stage and commit after re-verifying
that the index contains exactly the accepted new path.

## Validation and commit contract

Before commit:

- verify exact SHA-256 and Git blob identity for every bound artifact;
- verify both protected tag objects, targets, and tag-content hashes;
- verify both peeled historical commits remain non-ancestors of `HEAD`;
- verify tracker HTTP/dashboard projection and its integration `aq-qa` result;
- run doc-link validation and the full Tier-0 pre-commit gate with an index
  containing exactly the new settlement record;
- stop on unrelated staged content, broad validation mutation, or any failure.

Commit exactly one path in one ordinary non-merge commit. Then create a
separate post-commit verification artifact proving one parent, one changed
path, the accepted blob, unchanged protected refs, preserved non-ancestry, and
no historical-chain connection. That verification is a later documentation
slice and cannot be credited before it exists.

## Hard stops

Tracker not live-green; missing independent PASS; any protected evidence drift;
historical ancestry change; dirty index before staging; more than one staged
path; edit to the historical record; history/ref mutation; old-authority reuse;
or any assertion that Cycle 0 is closed before the additive settlement and
post-commit verification both pass.
