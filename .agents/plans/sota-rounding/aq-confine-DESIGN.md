### Requirements carried from the independent review of the earlier draft
1. Worktree metadata (`commondir`, `gitdir`, `HEAD` inside the worktree's admin dir, and the worktree's `.git` file) is bound read-only inside the sandbox. A writable admin dir was found to let the sandbox redirect where git reads its configuration from, which would make a later host-side git command execute attacker-chosen configuration. This is a hard requirement.
2. Every host-side git call on a confined worktree is hardened: explicit git dir and work tree, `core.fsmonitor` off, `core.hooksPath` disabled, no pager, no system or global config, never run with the current directory inside the worktree. A repo lint enforces it.
3. Object writes are quarantined per run (new objects go to a per-run directory; the real object store is read-only to the sandbox). After the run only objects reachable from the agent's own ref are imported, with strict verification (names recomputed from content, connectivity check against the real store alone).
4. The egress broker is a per-run subprocess with an empty environment, not a thread of the calling daemon. Kill targets the sandbox's own process group (recorded with its start time), never the caller. Resource limits are applied by wrapping the exec in `prlimit(1)`, not `preexec_fn`.
5. Egress policy is matched on the requested name before any DNS lookup; connections go only to global addresses (checked after unmapping IPv4-mapped IPv6, NAT64 rejected); CONNECT only, strict parser.
6. CI uses a scoped AppArmor userns profile for the test's bwrap binary, system binds that are bound only if they exist (non-Nix runners), and a probe before relying on confinement.
7. `--disable-userns` is on by default for every profile. Claude/Codex CLIs are not hosted in aq-confine (they could not function in a network-less, credential-less sandbox, and their own bwrap sandbox needs nested user namespaces), so the nested-sandbox conflict does not arise; the lane model is an owner confirmation (section 12).
8. Minimal-code cuts: no `restore-refs` verb (restore commands appear in the incident), no plain-HTTP forwarding, no `egress-wait`, grants scoped to the run only; in v6 also no `aq-hints` call, no per-lane prefix variants beyond one compact text, no DP-4 spool mirror.
9. Worktrees under `/tmp` (the owner's `/tmp/wt-*` layout) are allowed; the requirement is mount ordering (tmpfs first, binds after).
10. The host relay for service forwards is a per-run subprocess with connection caps, like the broker; its destination is a fixed table keyed by socket and never derived from bytes the sandbox sends.
11. Mirror requirements (header whitelist, no request bodies or query strings, allowlist on the raw request URI, per-run attribution by PROXY protocol, fixed cache key) are written requirements with tests (section 7.5, 10).
12. Guidance text visible to the agent consists of fixed template strings plus opaque ids; sandbox-supplied text appears only escaped, as data, in a structured field.
13. Total size caps apply to the object quarantine and to the worktree; the ref namespace directory is `lstat`-checked after every run.

## 1. Problem, goals, non-goals

### Problem
The repo has several independent bwrap argv builders that disagree on binds, env handling, resource limits and failure behavior (section 2). Notably DP-3's repro step (`scripts/ai/lib/oncalld_engine.py:763-786`) binds the whole root read-only, scrubs env by denylist (`:107-136`) and cannot run git; aider-wrapper fails open (`AI_AIDER_SANDBOX_FALLBACK_UNSAFE` default true, `ai-stack/mcp-servers/aider-wrapper/server.py:97-98`). Upcoming consumers (DP-3 implementers in W2-S3, REA in W1-S2, future MCP servers) would each add another builder. W2-S2 provides one launcher.

### Goals
1. One mechanism: build the bwrap argv from a named profile (data) plus validated overrides.
2. Allowlist semantics: env, mounts, network destinations. Nothing inherited from the caller.
3. Fail closed: no bwrap, no user namespaces, bad profile or out-of-policy path means refuse; never run unconfined.
4. Git works inside a worktree profile with the narrowest `.git` exposure that still allows `git add` and `git commit`.
5. Testable on a developer host and in CI with explicit skip semantics and hostile fixtures.
6. Observable: one structured line per launch, incidents for tamper, counters for the dashboard and health-spider.
7. Minimal code: reuse the existing bwrap flag vocabulary and the existing preflight idea; no new dependency in the core.

### Non-goals
Landlock, gVisor, microVMs, nsjail migration (W2-S4 verdict "monitor"); rootful namespaces or setuid helpers; replacing AppArmor (it stays the outer policy for the daemon, W2-S3); a syscall filter in S2a (profile key reserved for `--seccomp FD`); TLS interception; transparent or general network access; rewriting the execution-cell runner.

## 3. CLI contract and library

### Decision: Python module plus thin CLI
`scripts/ai/lib/confine.py` holds all logic; `scripts/ai/aq-confine` is a thin argparse wrapper. Python callers (oncalld, functional_eval, REA) want structured results and no shell round trip, and the repo idiom is exactly this split (`scripts/ai/aq-oncalld` puts `scripts/ai/lib` on `sys.path`). The command is on PATH already because `nix/home/base.nix:870` adds `scripts/ai` **[UNVERIFIED line, checked earlier this session on a previous main]**.

### Library
`load_profile(name)`, `preflight()`, `build_argv(profile, ...)` (pure, shared with `--explain`), `run(profile, argv, ...) -> ConfineResult` (status, rc, stdout, stderr, duration, profile, net, argv hash, reason, run id, refs report, egress summary), and `host_git(...)` (builds the hardened host-side git argv, section 5).

### CLI
```
aq-confine --profile NAME [--worktree PATH] [--net none|loopback]
           [--ro PATH]... [--rw PATH]... [--env-allow NAME]...
           [--timeout S] [--rlimit-as BYTES] [--explain] [--json] -- cmd [args...]
           [--allow-nested-userns]            (only if the profile permits it)
           [--egress-service llama|pypi|npm]... [--egress-optional]     (S2c-lite)
           [--egress-grant HOST:PORT]...                                (S2c-full)
verbs:     --preflight | --egress-status [RUN] | --egress-revoke RUN | --kill RUN
```
Only bwrap flags that exist in the installed bwrap are emitted (checked against `bwrap --help` on 0.12.0 earlier this session): `--unshare-all`, `--unshare-user` (required by `--disable-userns`), `--unshare-net`, `--unshare-pid`, `--die-with-parent`, `--new-session`, `--clearenv`, `--setenv`, `--ro-bind`, `--bind`, `--proc`, `--dev`, `--tmpfs`, `--dir`, `--chdir`, `--remount-ro`, `--disable-userns`, `--assert-userns-disabled`, `--seccomp FD`, `--json-status-fd`. `--share-net` is never emitted and a profile requesting it is rejected at load.

Argument rules:
- `--ro/--rw`: absolute paths, resolved with `realpath` on the host, rejected if `/`, under the secrets locations (`/run/secrets`, `~/.ssh`, `~/.gnupg`, `~/.config/sops`), or reaching outside the requested prefix via a symlink. `--rw` is limited to the profile's `rw_allowed_roots`.
- `--worktree`: required when the profile needs one; must be a linked git worktree under an allowed root (the delegation worktrees dir, mirroring `verify_worktree_containment`, `scripts/ai/lib/oncalld_engine.py:139-161`). `/tmp` worktrees are allowed.
- `--net` may only tighten the profile ceiling.
- `--env-allow NAME`: must match `^[A-Z][A-Z0-9_]*$` and not the hard-deny pattern (token, secret, key, auth, passw, cred, sops, cert, ssh, `GH_`, `GITHUB_`, `AWS_`); a denied name is a usage error, not a silent drop.
- Everything after `--` is exec'd as an argv vector, never through `sh -c`.

### Exit codes and result line
| Code | Meaning |
|---|---|
| child code | passed through |
| 64 | usage error / forbidden path / denied env name |
| 70 | confinement unavailable or setup failed (child never ran) |
| 71 | profile missing or invalid |
| 72 | policy violation: ref tamper, object import failure, or egress burst kill (a single denial never causes 72) |
| 124 | timeout |
| 137 | child SIGKILLed (rlimit / OOM) |

The last stderr line (or stdout with `--json`) is one JSON object: status (`ok|child-failed|setup-failed|timeout|usage|profile-error`), rc, run id, profile, net, worktree, duration, argv hash (never the argv or env), reason, limits, `refs` report, `egress` summary, timestamp. bwrap setup failure is told apart from child failure using `--json-status-fd` (no `child-pid` event means setup failed), not stderr parsing.

### Process model
The launcher starts the bwrap command, wrapped in `prlimit(1)` for the resource limits, with `start_new_session=True` and no `preexec_fn` (unsafe in processes with threads). It records the process group, bwrap pid and `/proc` start time in the run directory. **Kill semantics (V4):**
- **In-process path** (library `run()`): the launcher signals through the `Popen` handle it holds, so the pid cannot be recycled before the child is reaped. `run()` watches for the broker's `kill-requested` marker with a short poll (about 1 s) for the lifetime of the `Popen` object (a small watcher thread is acceptable; the poll is the minimum), and on timeout or marker performs **SIGKILL on the bwrap process and its group** (not a bare SIGTERM to the group: the sandbox uses `--new-session`, so its processes leave the launcher's group; killing the outer bwrap with `--die-with-parent` and `--unshare-pid` tears the pid namespace down). A test uses a child that ignores SIGTERM.
- **Marker versus normal exit (precedence):** if the marker is present when the child is reaped, the status is 72 `egress-burst` even when rc is 0, and the caller quarantines; a marker written after the child has been reaped is ignored and removed.
- **CLI path** (`aq-confine --kill RUN`, which has only a pid and a recorded start time): open `os.pidfd_open(pid)` first, then verify the recorded start time from `/proc/<pid>/stat`, then signal through the pidfd (`signal.pidfd_send_signal`); a check-then-`kill(pid)` has a recycling window and is not allowed.
- **Orphans:** the broker and relay exit on parent-pipe EOF (or `PR_SET_PDEATHSIG`) as in 7.2; the sandbox itself dies through `--die-with-parent`.
- **Marker location:** the marker, guidance directory and process records live in a run-dir parent the sandbox cannot reach; the only sandbox-writable binds are the specific private subdirectories (quarantine, private ref and reflog directories). A test asserts the sandbox cannot create or delete the marker.
The caller's own pid is never a kill target. Components that must end a run (the broker, 7.6) never signal anything themselves: they write the marker and the launcher performs the kill.

### --explain
Prints the exact bwrap argv and env names (not values) without launching; tests compare against golden files so any widening of mounts shows as a review diff. Goldens assert `--unshare-user` and `--disable-userns` together for every profile (bwrap rejects `--disable-userns` without an explicit `--unshare-user`).

## 5. Environment and git handling

### Env: allowlist built from scratch
The launcher emits `--clearenv` and then sets exactly: profile `env_base`, profile `env_allow` names present in the caller env, explicit `--env-allow` names (hard-deny checked), `PATH`, `HOME` (a tmpfs), and `AQ_CONFINED=<profile>`. The host-side bwrap process itself is started with a minimal environment. This replaces DP-3's denylist (`scripts/ai/lib/oncalld_engine.py:107-136`), which passes unknown secret-bearing names (backlog 6160b). `GIT_*` is rebuilt explicitly (below) instead of blanket-denied.

### Why git needs care
A linked worktree's `.git` is a file pointing into `<common>/worktrees/<name>`. With only the worktree bound, git inside the sandbox cannot find its repository (backlog 6160c). Binding the whole common `.git` writable fixes that but lets the sandbox change configuration, hooks and every ref that the host will later trust. Two further findings from the independent review shape the final design, stated here at design level:
- The per-worktree admin directory contains files that decide **which repository and which configuration git uses** (`commondir`, `gitdir`, `HEAD`, plus the worktree's own `.git` file). If the sandbox can write them, it can steer a later host-side git command at attacker-built configuration, which can execute commands on the host. These must be read-only inside the sandbox.
- Writable object storage lets the sandbox replace objects that other branches rely on, with no ref change to notice. Object writes must be quarantined.

### Binding (profile `git: "worktree"`)
Preconditions checked on the host before launch: the worktree's git dir must be `<common>/worktrees/<name>`; repositories that enable `extensions.worktreeConfig` are refused; per-run **private ref and reflog directories** are created in the run state dir and **seeded** with a copy of the claim's current loose ref file(s) and reflog (binding an empty directory would hide an existing loose ref; a claim ref that exists only in the read-only `packed-refs` needs no seed, and the first commit creates a loose ref in the private directory); a per-run object quarantine directory is created in the run state dir. The seed copy is made by the host, regular files only, no symlink following.

Mount order (later mounts layer over earlier ones; tmpfs mounts always come first, which is what makes worktrees under `/tmp` work):
1. System read-only binds that exist, `/proc`, `/dev`, tmpfs `/tmp`, tmpfs HOME, scratch tmpfs.
2. The whole common git dir read-only (config, hooks, packed refs, the real object store, everything).
3. This worktree's admin dir writable (index, per-worktree logs), then **read-only overlays** on `commondir`, `gitdir`, `HEAD` in that dir and on the worktree's `.git` file.
4. The per-run object quarantine writable, with `GIT_OBJECT_DIRECTORY` pointing at it and `GIT_ALTERNATE_OBJECT_DIRECTORIES` at the real (read-only) store.
5. The **private** ref directory and **private** reflog directory (run state dir, seeded as above) bound writable **over** the real paths `refs/heads/aq/<claim>` and `logs/refs/heads/aq/<claim>` (bwrap binds a source onto a different destination). The real ref and reflog directories are never bound writable, so the real repository's refs are unchanged for the whole run.
6. The worktree itself writable; then, if `readonly_root`, `--remount-ro` on `/tmp` and `/` (after step 1's scratch mounts exist; remount is non-recursive so separate mounts keep their own flags); then `--chdir` to the worktree.

Consequence: `git add` and `git commit` work on the claim branch; switching branches inside the sandbox is blocked because `HEAD` is read-only (implementers are pinned to their claim branch); writes to config, hooks, other branches and existing objects fail. These behaviors were observed on this host with git 2.54 and bubblewrap 0.12.0 during the design round; the conclusions are reproduced as required tests in section 10, not as recipes here.

Sandbox git environment: no system or global config, no terminal prompts, no optional locks, `gc.auto=0` and `maintenance.auto=false` (an incidental auto-gc otherwise fails noisily on the read-only common dir), `safe.directory` set to the worktree, identity only from `--env-allow` or profile defaults. No credential helper, ssh or network: pushing is impossible by construction. A claim branch that is already packed still commits (the new loose ref overrides it); no "branch must be loose" precondition.

### Host-side git rule (requirement, with lint)
Every host-side git call on a confined worktree, by the launcher and by any caller after a run (W2-S3 diff, commit, merge, promote), must use explicit repository selection and neutralised config, and must never run with the current directory inside the worktree: explicit `--git-dir` (the worktree's admin dir) and `--work-tree`, `core.fsmonitor=false`, `core.hooksPath=/dev/null`, no pager, external diff and attribute/exclude files neutralised (`core.attributesFile`, `core.excludesFile`, `diff.external`), `protocol.allow=never`, empty askpass, `GIT_CONFIG_NOSYSTEM=1`, `GIT_ATTR_NOSYSTEM=1`, global config `/dev/null`. Reason: the sandbox can create embedded repositories inside the worktree whose configuration a cwd-based git would honor. `confine.host_git()` builds this argv; a lint fails if **any script that takes a confined worktree path** (grep for scripts referencing both a worktree variable and git, starting with `confine.py` and `oncalld_engine.py`) spawns git without an explicit git dir; `host_git` is the only sanctioned path in the docs. Documentation note for the owner: do not `cd` into subdirectories of an agent worktree and run git before the post-run embedded-repo check has passed, because interactive git outside `host_git` honors repository configuration found there. DP-3's worktree creation already passes `core.hooksPath=/dev/null` (`scripts/ai/lib/oncalld_engine.py:730`) but selects the repo by cwd, so W2-S3 must adopt `host_git`.

### Promotion: import, then update-ref (V1, V2)
Why private ref directories: if the sandbox wrote the real ref while its new objects existed only in the quarantine, the real repository would hold a ref to a missing object for up to the run timeout (and indefinitely if the run is killed or the launcher crashes before import), breaking any host git command that walks all refs. With private directories a killed run changes nothing in the real repository and symlink, hard-link or file-count pollution never reaches the real tree.

After the run (any status), the host treats **both the private ref directory and the quarantine as hostile data**: it never follows symlinks in either (regular-file-only traversal for size and content checks; deletion that does not follow links), ignores any `info/alternates` the sandbox wrote in the quarantine (the host supplies its own alternate list), and prunes them with non-following deletion.
1. **Validate the private ref directory** (this is where the former `lstat` rules now run, on a directory the host owns): only regular files, names matching `[a-z0-9-]{1,40}`, at most 64 entries, each file a single well-formed object name. Anything else is `ref-foreign-changed` and is not promoted.
2. **Enumerate and import for every accepted ref**, not only the own branch: for each accepted ref's new tip run `rev-list --objects --missing=error <new tips> --not <all refs outside the sandbox's writable set>` (so a ref the sandbox created fresh has a well-defined base), with the quarantine as an alternate for this step only.
3. **Pin the mechanism:** pipe those names into `pack-objects --stdout`, and that pack into `index-pack --strict --stdin` (or `unpack-objects --strict`) running against the **real store with alternates unset**. These modes recompute every object's name from its content and run object-level fsck; a planted object under another name is either stored under its true name as an unreferenced object (harmless, later pruned by gc; expected and not a store modification) or the import fails. Copying files, `repack`, or reusing the quarantine as an alternate does not verify names and is not acceptable.
4. **Connectivity check** of every accepted new tip against the real store alone (no alternates).
5. **Promote:** only after steps 1-4 pass for a ref, run `update-ref <ref> <new> <old>` on the real repository (via `host_git`), with the old value checked so a concurrent move fails safely (reported, not forced). A ref that fails any step is not promoted and is reported as `object-import-failed`; refs that pass are promoted independently.
The import runs before `refs-after` is recorded. Total size of the quarantine and of the private ref directory is capped (size-limited tmpfs for the quarantine, or a post-run size check), since `RLIMIT_FSIZE` is per file only; the worktree has a total size cap as well, checked after the run and periodically for long runs. The mismatched-name hostile fixture is a **required acceptance test** for S2a (expected: planted object stored under its true name or import fails; the original object is byte-identical; a leftover unreferenced object is not a failure).

### Refs: namespace prevention, detect-and-flag backstop
Branch naming is `aq/<claim>/<slug>`. In `git_refs: "namespace"` mode (default) only that namespace is writable, and only as a **private copy** (see promotion above), so writes to any other branch fail, and the real refs under `aq/<claim>/*` change only when the host promotes them. Mode `heads` binds a private copy of the loose refs under `refs/heads` instead (packed refs stay read-only through the common dir); there the host promotes only the own branch and every other changed ref is `ref-foreign-changed` and not promoted. Branch deletion inside the sandbox fails (needs the packed-refs lock in the read-only common dir); cleanup is a host action.

Detection, both modes: on the host, via `host_git`, snapshot before and after every run: all real refs (name, object, type; the after-snapshot is taken after promotion), the main `HEAD` and the worktree admin files (`HEAD`, `commondir`, `gitdir`, `config.worktree`), hashes of `config`, `packed-refs` and the worktree `.git` file, and a name/mode/hash listing of `hooks/`. The pre-launch snapshot is saved under the run state dir with mode 0600. "Own branch" is the branch named by the worktree `HEAD` before launch, plus anything under the claim namespace.

| Kind | Meaning | Effect |
|---|---|---|
| `ref-foreign-changed` | the private ref directory held an entry outside the accepted set, a bad name, a non-regular file, or too many entries; or (heads mode) a non-own branch changed | high; fails the run; the offending entries are not promoted |
| `ref-own-rewritten` | own ref moved to a non-descendant of its old tip | medium; fails the run only with `strict_history: true` (DP-3 sets it) |
| `protected-file-changed` | common `config`, `packed-refs`, `hooks/` or main `HEAD` differ | high; fails the run (tripwire proving the read-only mount held) |
| `worktree-metadata-changed` | worktree admin files or `.git` file differ, or an embedded `.git` was created in the worktree | high; fails the run |
| `object-import-failed` | quarantine import or connectivity check failed | high; fails the run |

Concurrency rule (simpler with private refs): the sandbox can no longer change real refs at all, so a change to a real ref outside the promoted set between the two snapshots is by construction another actor (the owner committing on `main`). It is recorded as `concurrent-actor` information and never fails the run. `ref-foreign-changed` now means "the sandbox's private ref directory contained something outside the accepted set or failed validation". `protected-file-changed` and `worktree-metadata-changed` remain tripwires for the read-only overlays. How often concurrent movement occurs in practice is **[UNVERIFIED]**; counters will tell.

Recording and surfacing: result status `child-failed`, reason `ref-tamper` (or `object-import-failed`), exit 72, `refs` report in the result line and library result; a telemetry event; counter `ref_tamper_total{kind,suspect}`; and an attention-queue incident, `push("aq-confine","high","human_gate", title="aq-confine ref-tamper run <id8> (<caller>)", ...)` (`scripts/ai/lib/attention_queue.py:237`, `AlertSpec` at `:66`), whose `proposed_action` lists the exact commands to inspect the saved private directory and, where a promotion happened, the exact `update-ref` commands to restore each promoted ref from the saved pre-snapshot. There is no restore verb (cut); the owner runs the printed commands. The incident reaches `aq-approve` (`scripts/ai/aq-approve:126` executor table, `:147` `_resolve_actor`) and the dashboard approvals view (`dashboard/backend/api/main.py:243-245`). Whether `scripts/ai/aq-health-spider` lists alerts by source is **[UNVERIFIED]** (it imports `push/get_pending/resolve` at `:50`); confirming it is an S2a acceptance gate. A global high alert fires if tamper occurs in three or more runs within an hour. Callers must not promote a claim that returned 72.

Files inside the worktree that the host later acts on (`.gitattributes` filters, `.githooks/`, pre-commit configs) are content produced by the confined process: a review concern, mitigated by the host-git rule, not by a mount.

## 6. Failure semantics and observability

### Fail closed
1. Resolve bwrap from `$BWRAP_PATH`, else `PATH` (same rule as `ai-stack/switchboard/execution_cell_runner.py:313`; the Nix service sets `BWRAP_PATH`, `nix/modules/services/execution-cell-runner.nix:99`). Missing: exit 70, reason `bwrap-missing`.
2. Preflight (cached per process, short TTL), same shape as `confinement_preflight` (`execution_cell_runner.py:323`) but **portable**: it binds the profile's existing `ro_system` entries and runs the host interpreter resolved with `realpath`, instead of assuming `/nix/store`. Any non-zero exit: exit 70, reason `userns-unavailable`. One real probe covers every cause (NixOS `security.allowUserNamespaces=false`, Ubuntu `kernel.apparmor_restrict_unprivileged_userns`); sysctls are only read to enrich the reason text. On this host `kernel.unprivileged_userns_clone` and the Ubuntu sysctl do not exist, and `user.max_user_namespaces` is 111253.
3. No `--unshare-user-try`, no `--share-net`, and no code path that executes the caller's command without bwrap. There is deliberately no unsafe fallback flag. A static test fails the suite if `confine.py` spawns anything other than bwrap/prlimit and the hardened git probes.
4. Library callers receive `status="setup-failed"` and decide to defer (DP-3) or refuse (functional_eval). Output is never returned for a command that did not run confined.
5. `--net loopback` is `--unshare-net` with bwrap's private `lo`. It is not the host loopback: the sandbox cannot reach llama.cpp or the coordinator through it. Reaching permitted host services is section 7.

### Isolation properties asserted by tests
Abstract unix sockets are unreachable under `--unshare-net` (so host D-Bus/X abstract sockets are blocked) and the filesystem session bus is not bound; nested user namespaces fail by default; inherited fds are limited to 0-2 plus the status fd; `/sys` is not mounted; a profile that would drop `--unshare-net` is rejected at load.

### Observability
- One JSON line per launch appended to `${AQ_TELEMETRY_DIR:-/var/lib/ai-stack/hybrid/telemetry}/aq-confine.jsonl` (the directory that already holds `aq-usage.jsonl` and `agent-run-events.jsonl`); append failures never change the result. Lines are written with a single append, kept under 4096 bytes (so concurrent runs cannot interleave), contain no env values and no child argv, and the file rotates (50 MiB, keep 3). Per-connection egress lines are capped per run.
- Counters derived from that file: `launches_total{profile,status}`, `setup_failed_total`, `timeouts_total`, `ref_tamper_total{kind,suspect}`, egress counters (section 7), `broker_died`, `last_preflight_ok_ts`. A non-zero `setup-failed` rate where confinement is expected is the alert condition; the W2-S3 dashboard card's `confined=true` means "last launch not setup-failed within N minutes and the feature flag on".
- `aq-confine --preflight [--json]` exits 0/70 for QA (`scripts/ai/_aq-qa-bash` already checks bwrap presence near `:2639`).
- Run state: `${AQ_CONFINE_STATE_DIR:-$XDG_STATE_HOME/aq-confine}/runs/<run_id>/` (0700): ref snapshots, object quarantine, guidance directory, process-group record, broker pid, egress grants; pruned after 14 days.

## 7. Network egress (brokered), package mirrors, denial guidance

Owner constraints: agentic dev speed must not suffer, and safety, metrics and observability must be good enough to respond. Design: egress is a **brokered capability**, never a network. The sandbox always has `--unshare-net`; each permitted path is an explicit, logged, revocable entry decided by policy without a human where the profile declares it, and by a human (existing approval queue) otherwise.

### 7.1 Existing control surfaces (checked) and what is reused

|---|---|

| Dashboard approvals `dashboard/backend/api/main.py:243-245` | Display of pending requests; no new UI |

| systemd `IPAddressAllow/Deny` on service units (e.g. `nix/modules/roles/ai-stack.nix:1123-1127`) | Outer cap: the broker runs in the caller's cgroup, so the unit's rules bound any grant |

No per-destination egress engine or main switch exists for subprocess traffic, so the design adds the smallest one.

### 7.2 Mechanism
Network namespace `none` plus a unix-socket bridge to a host-side broker. A filesystem unix socket bind-mounted into the sandbox crosses the netns boundary; abstract sockets do not. `AF_UNIX` paths are limited to 108 bytes, so sockets live at a short path (`$XDG_RUNTIME_DIR/aqe/<run8>/`, mode 0700, bound read-only at `/run/aqe/`). pasta/passt and slirp4netns give only L3/L4 filtering and are not installed here (`passt` exists in nixpkgs); they remain a fallback for tools that ignore proxy settings. Landlock network rules are a non-goal.

Components: (1) a **per-run broker subprocess** (`python -I`, empty environment, no secrets) started by the launcher and killed with the run, so a parser bug fed by sandbox bytes cannot reach the calling daemon's environment or tokens; broker death drops tunnels only. (2) An **in-sandbox supervisor** (stdlib, small) exec'd by bwrap only when egress is brokered: it listens on private loopback ports (the same port numbers as the host services, so `LLAMA_URL` works unchanged), relays each connection over `/run/aqe/*.sock`, runs the command as a child and returns its exit code. (3) Policy file `config/confine-egress-policy.json` (S2c-full), loaded from the checkout, never from the worktree.

**Host relay for service forwards (S2c-lite).** Also a per-run subprocess (`python -I`, empty environment), never a thread of the caller, so descriptor exhaustion or event-loop starvation by a hostile client cannot hurt the calling daemon. Its destination is a **fixed table keyed by the socket** (service name to one host:port); it interprets no preamble and derives nothing from bytes the sandbox sends. Limits, enforced in the relay (it sees connections, not request boundaries):
- per-run connection cap for every service;
- an **idle timeout on relay connections** (default 30 s with no bytes in either direction), so an HTTP client pool cannot pin slots with idle keepalive connections;
- for `llama`, a **global concurrency cap across all runs** (default 2 in-flight connections machine-wide, plus an optional per-run cap of 1 so one run cannot take both), implemented as a small lease set of `flock` slot files in the state dir shared by every relay; excess connections **queue with a short timeout (default 10 s) and are then refused** with a fixed guidance reply, which is friendlier to aider and the Qwen runtime than an immediate refusal. This is what protects the owner's other lanes from a single slow shared model (about 5 tok/s), which a per-run count alone cannot do with N concurrent runs.
- lease cleanup: slots are `flock` locks, so a crashed relay releases them automatically; the state-dir pruner removes stale slot bookkeeping.
**Mirror transport (V3, decided):** the mirrors use the same per-run relay in front of an nginx listener; **relay + PROXY protocol v2 is the chosen design** (see R4). The earlier wording that exposed mirrors as nginx unix sockets bound directly into the sandbox is dropped, because with no relay there is no per-run attribution, no per-run rate limit and a shared connection pool across runs. nginx listens on a **unix socket with `proxy_protocol` enabled**, so no TCP loopback port exists for mirrors; the socket is root-owned (or owned by the nginx user), mode so that only the relay processes can connect, and is never bound into any sandbox.
**Process lifetime:** the broker and the relay each exit when the pipe from their parent (the launcher) reaches EOF, or set `PR_SET_PDEATHSIG`, so a hard-killed launcher or caller cannot leave them lingering with live sockets; the state-dir pruner also removes stale sockets.

Making coordinator or switchboard reachable is **S2d, its own slice**, and it is not a variant of the relay or of the CONNECT proxy. The agent-auth design (`agent-auth-DESIGN.md` in this directory, reviewed here only for this dependency, **[UNVERIFIED]** otherwise) requires the launcher's broker to hold a run-bound token and add a grant header to forwarded requests, and the coordinator's sandbox listener to be reachable only through that broker. Adding a header requires parsing HTTP, so S2d is a third component: an **L7 grant-injecting forwarder** with a strict request parser, per-service method and path allowlist, run-bound token injection and response filtering. It sits on the same trust boundary as the S2c-full parser and carries the same adversarial review gate. Agent-auth v2 is in revision (it pulls the switchboard guard forward and binds `run_id` to the launcher); S2d stays NOT_READY until that revision is reviewed, and until then coordinator and switchboard are not grantable. The agent-auth text also assumes the local-Qwen loop runs inside aq-confine; in this design only its tool subprocesses are confined and the runtime stays on the host (7.6), which agent-auth must reconcile.

### 7.4 Policy engine (S2c-full; first match wins)
1. Parse the CONNECT target strictly. **Policy is matched on the literal requested name or IP before any DNS lookup**; no match means deny with no resolution (prevents DNS-label exfiltration). Strict parser: CONNECT only (other methods get 405; no plain-HTTP forwarding), host charset and length caps, port 1-65535, small header cap, no pipelined bytes before the response.
2. IP literals must be global. Global check: unmap IPv4-mapped IPv6, then require `is_global`; additionally reject NAT64. This covers loopback, RFC1918, link-local (v4 and v6), CGNAT, multicast, unspecified. No wildcard allow rules.
3. Run revocation tombstones.
4. Allow rule or run grant matched: resolve host-side, require **every** answer to be global, connect to that checked address only, never re-resolve.
5. Otherwise deny (class `nogrant`), steer (7.6), log, file a request.

Requests: one deduped attention-queue alert per (run, destination), executor `confine_egress_grant`, scope "this run" only, expiry = run timeout. Destination strings pass a strict hostname regex and length cap before reaching the alert or dashboard; at most 5 pending requests per run and 20 per hour, beyond which requests auto-deny with one high alert; pending requests expire with the run; the executor validates the run id as a UUID and does nothing for dead runs; grant files are replaced atomically and read by `(inode,size,mtime_ns)`.

Residuals stated: domain fronting through an allowed CDN name; anonymous-write hosts are upload channels; CONNECT tunnels are opaque. Per-destination byte caps (default 5 MiB per non-service destination per run) and per-connection logging bound them.

### 7.5 Baseline: read-only package caches (owner decision)
CONNECT-only TLS cannot see HTTP methods, so a hostname allowlist cannot make a host read-only if the same host accepts writes. `registry.npmjs.org` serves `npm publish` as a PUT on the same host as downloads: an agent that is handed an attacker's token in its prompt could publish worktree contents publicly. The PyPI index host cannot be proven read-only here (uploads are directed at `upload.pypi.org`, but whether `pypi.org` also accepts an upload path is **[UNVERIFIED]**). `files.pythonhosted.org` is download-only; `cache.nixos.org` has no client write API but also no consumer, since the sandbox has no nix client or daemon socket.

Chosen design: **nginx read-only reverse-proxy mirrors on host loopback** (nginx is already deployed, `nix/modules/services/ingress.nix:73`; nixpkgs also has `devpi-server` (PyPI only), `squid`, `harmonia`, `nix-serve-ng`; `verdaccio` is not in nixpkgs, checked in the v5 round). The sandbox reaches them through the per-run relay (7.2) in front of an nginx unix-socket listener with PROXY protocol; `PIP_INDEX_URL` and the npm registry setting point at the mirror. No TLS interception, no CONNECT path for packages.

**Written requirements for the mirror module (S2e).** These replace the v5 blacklist-style wording and each has a test (section 10):
- **R1 header whitelist (M1).** Request headers are not passed through. Only a fixed `Host` (the upstream), a fixed `User-Agent`, `Accept`, and an identity `Accept-Encoding` are sent upstream. Anything else, including credentials, cookies and arbitrary headers (which would otherwise reach the registry operator's logs), is dropped by construction rather than by listing bad names.
- **R2 no bodies, no queries (M2).** Request bodies are not forwarded; the client body cap is tiny; any request with a non-zero content length or a transfer encoding is rejected with 400; any request with a query string is rejected, since index and artifact fetches need none. Only GET and HEAD are accepted.
- **R3 allowlist on the raw request URI (M3).** The path allowlist is evaluated on the raw request URI, not only the normalised one, because the upstream path is forwarded from the raw form. A map rejects percent-encodings, dot segments, doubled slashes, semicolons, backslashes and non-ASCII before the location match (PyPI versions with a plus sign use the literal character). The upstream host in `proxy_pass` is fixed and uses no request-derived variable; `proxy_ssl_server_name` and upstream certificate verification are on; the default server closes the connection; `server_name` is pinned; no request header or `Host` value influences routing, upstream selection or the cache key. Path length is capped (200 bytes).
- **R4 per-run attribution (M4, V3 decided).** The relay is a raw-TCP process, so nginx would see one source for every run. The per-run relay therefore **prepends a PROXY protocol v2 header** (no HTTP parsing) carrying a **synthetic per-run source address** from 127.0.0.0/8, and nginx's PROXY-enabled unix listener keys `limit_req_zone`, `limit_conn_zone` and the access-log format on `$proxy_protocol_addr`. No forgery path exists from the sandbox: the relay writes the header first and anything the sandbox sends follows as request bytes, which nginx rejects as a malformed request line if it looks like a header. Required details: (a) **allocation and mapping:** the launcher allocates the synthetic address from a pool recorded in the state dir as a table `address -> run_id, start time, expiry`; an address is not reused while its run is live or until its log lines have aged out (the table keeps an entry for a retention period after the run ends, so attribution never collides); a log-reader helper maps `$proxy_protocol_addr` back to a run id; (b) nginx trusts PROXY headers only on that unix listener, whose file mode admits only the relay processes; (c) default limits 120 requests per minute and a small concurrent-connection cap per synthetic address; (d) tests: one run's flood cannot exhaust another run's budget, and the access-log line carries the run's synthetic address which resolves to the right run id after the run ended. The statements "per run" and "which run fetched what" hold because of this requirement and would have to be dropped under any direct-bind variant.
- **R5 rewriting and redirects (M5).** Upstream bodies are requested uncompressed so URL rewriting works; absolute upstream URLs in PyPI simple pages and JSON and in npm package metadata (`dist.tarball`) are rewritten to the mirror for an explicit content-type list, without the once-only limitation, with buffers sized for large metadata documents. Upstream redirects are not rewritten generically: a 3xx to a host that is not mirrored becomes a fail-closed 502 with guidance text. Dependencies that resolve to other hosts (git URLs, direct tarball URLs) fail with `nonglobal`-style guidance instead of hanging. The listener speaks HTTP/1.1 only, bounds keepalive requests, rejects underscores in headers and invalid headers, and request buffering stays on.
- **R6 cache hygiene (M6).** The cache key is fixed to scheme, upstream host and URI only (no `Host`, `Range`, encoding or cookie components); upstream `Vary` influence is ignored; index documents get a short TTL and no stale-on-error, immutable hash-addressed artifacts a longer TTL; the cache lock is on; slicing is not enabled; temp-file and cache sizes are capped. Only the configured registry hosts are mirrored (scoped registries elsewhere fail closed).
- **R7 residual (M7).** Package-name or path data sent to a public registry has no return channel; it is bounded by the path cap and the rate cap in R4.

Dev speed: a cache hit is served from local disk and should beat a direct fetch; a miss costs one extra hop. Real PyPI and npm behavior for R5 is **[UNVERIFIED]** and is S2e acceptance. **S2e status: PLAN_READY_WITH_FOLLOWUPS per the confirmatory review, with the transport question (V3) resolved as relay + PROXY protocol v2.** It is default OFF (enabling is an owner `nixos-rebuild switch`), last in the slice order, and no other slice's acceptance depends on it. When disabled, a `pypi`/`npm` request fails closed with `service-down` guidance; nothing falls back to direct network. `cache.nixos.org:443` remains a baseline CONNECT entry for S2c-full, inert until a consumer exists.

Residual risk, honestly: (1) a sandbox can still send GETs to public registries through the mirror with small amounts of data in the path (bounded by the path and rate caps, logged); the attacker cannot read the registries' logs, so there is no return channel. (2) The cache is shared across runs: a run can fill it (bounded) and hit timing can reveal what other runs fetched; cached content is only what upstream served. (3) Fetched packages are untrusted code that runs inside the confined sandbox; anything promoted out goes through normal diff review (`deployment.npmSecurity` covers the repo's own lockfiles). (4) Upstream compromise and typosquatting are not addressed.

### 7.6 Denial guidance, lane model, escalation
**Lane model (recommended default; owner confirms, D2).** A confined run has no network namespace access, no OAuth credentials and no route to the Claude or OpenAI APIs (only llama and the package mirrors are grantable), so the Claude and Codex CLIs cannot function inside it at all. Allowing nested user namespaces for them would not defeat the outer mounts by itself, but would hand the sandbox capability-bearing user namespaces, the largest unprivileged kernel attack surface, with no seccomp filter in S2a; their inner sandboxes are also weaker than ours on every axis we configure. So, in this program:
- Claude and Codex implementers keep their native sandbox, configured by the harness, and are covered by worktree isolation, review and the host-git rule. They are **not** hosted in aq-confine. Per the owner's D2 answer they keep **default outbound access, but it is monitored and filtered** (section 7A, slice W2-S7); they are not network-less.
- aq-confine hosts: (a) local-Qwen tool subprocesses (the Qwen runtime stays on the host and launches its tools through `aq-confine`), (b) REA, (c) eval, (d) aider.
- `--disable-userns` stays the default for every profile; no profile permits nesting.
- If the owner later wants Claude/Codex inside aq-confine, that is a separate design: a broker-granted API host with broker-side credential injection (the same pattern as agent-auth), plus a per-lane switch for the inner sandbox verified by test.

**What exists for hints:** `aq-hints` (`scripts/ai/aq-hints`), the coordinator hints route (`ai-stack/mcp-servers/hybrid-coordinator/http_server_impl.py:459`), the local agent's `get_hints` tool (`ai-stack/agents/runtimes/local_agent_runtime.py:177`), and the DP-4 guidance spool (`dashboard/backend/api/routes/aistack.py:6569` dir from `AQ_AGENT_GUIDANCE_DIR`; write `:6755`; read `:6810`). The spool has no agent consumer that I found (backlog already notes "no consumer ack", `.agent/memory/issues-backlog.md:6159`) and coordinator hints are not reachable from the sandbox. v6 therefore cuts the speculative parts: **no `aq-hints` call, no hints registry entry, no DP-4 spool mirror, no per-lane prefix variants** (one compact text).

**Design: a host-rendered read-only guidance directory.**
1. At launch the launcher creates `<state>/runs/<run_id>/guidance/` and binds it read-only at `/run/aqg/` as a **directory bind** (never a single-file bind: a rename-replace would leave the sandbox with a stale inode), with `AQ_CONFINE_GUIDANCE=/run/aqg/GUIDANCE.md`. `GUIDANCE.md` is rendered from reviewed fixed templates in `config/confine-guidance.json` (one compact text; sanctioned paths for the profile). `denials.md` starts empty.
2. The host appends to `denials.md` with `O_APPEND` on a regular file it created (`O_NOFOLLOW`), never by rename, writing each entry as a single `write()` of a complete line (a reader may otherwise see a partial line); the sandbox sees appends live and cannot write, replace or create symlinks in the directory.
3. **Fixed strings and opaque ids only.** The 403 reason phrase (at most 100 characters) and the first lines of every `denials.md` entry consist only of fixed template strings and an opaque denial id (no request data, so no CR/LF/NUL injection into the HTTP status line). A denied destination appears only in a structured field after escaping: strict hostname regex, ASCII only, at most 253 characters, no control characters, rendered inside a code span. Sandbox-supplied text is data everywhere it later shows up: attention-queue titles and details, `aq-approve`, the dashboard, and any handoff or commit text the agent writes after reading `denials.md`; the queue and dashboard must render it escaped.
4. Where no broker exists (egress `none`, and the S2c-lite forwards) there is no per-denial event; steering is the launch-rendered file plus the local-Qwen runtime's prompt prefix, which says network errors are expected and lists the sanctioned paths.
5. How curl, pip, npm and git surface the 403 reason phrase is **[UNVERIFIED]**; the tests record it.

Classes and the fixed steer for each: `nonglobal` (not reachable by design; use the model URL and the package mirrors), `nogrant` (a request was filed; continue offline; do not retry in a loop), `service-down` (not enabled on this host; report it in the handoff), `cap` (rate limit; wait).

**Delivery per lane in this program:** local Qwen: runtime on the host, tool subprocesses confined, compact prefix in the system prompt, tool results carry the 403 text, `get_hints` works host-side. Aider: guidance file only. REA and eval: guidance file only (no egress). Claude and Codex: not hosted, so their existing guidance files (`CLAUDE.md`, `AGENTS.md`, lane references) apply unchanged; anything an agent writes into those worktree files is its own prompt and promoted content that goes through diff review.

**Escalation: deny and steer first; kill only on loops or cumulative abuse** (all figures are heuristic and **[UNVERIFIED]**, tune after the first week of counters; D3):
| Trigger | Response |
|---|---|
| any denial | deny, steer, log, count; full text for the first 3 per class, then a one-line form |
| first denial of a class in a run | one deduped alert (medium; `nonglobal` is high) |
| 10 or more denials in 60 s | high alert, wording switches to "stop retrying" |
| 10 `nonglobal` attempts in 10 minutes, or a lifetime per-run `nonglobal` cap | kill the run (exit 72 reason `egress-burst`, incident, claim quarantined) |
| **cumulative per-run caps: about 300 denials, or about 40 distinct denied destinations** | alert only in the first week; kill after tuning |
| 30 or more denials in 60 s, or the same destination 40 times in 5 minutes (counted per distinct request attempt, with retries coalesced in a 10 s window) | alert only in the first week; kill after tuning |
Rationale: every denial is uniform (no DNS, same 403), so a slow scan learns nothing and the cumulative caps close the slow-scan hole; package managers retry several times per request, so same-destination and rate triggers must not false-kill honest retries, and a false kill loses a run's work. Enforcement path: the broker (a subprocess with an empty environment) writes a `kill-requested` marker; the launcher, which owns the pgid and start time, kills. If the broker dies, burst detection disappears while the sandbox still has no network, which is safe; this increments a `broker_died` metric.

### 7.7 Observability, revoke, latency, fail-closed
- Per-connection JSONL events: time, run, profile, caller, destination host and port, resolved class, decision (`allow-service|allow-grant|deny-nogrant|deny-nonglobal|deny-revoked|deny-cap`), rule, bytes each way, duration, guidance id. Never paths, headers or bodies. Metrics: `egress_connections_total{decision}`, `egress_denied_total`, `egress_bytes_total{profile,direction}`, `egress_open_tunnels`, `egress_requests_pending`.
- Inspect: `--egress-status [RUN]` (effective rules, grants with approver and expiry, pending requests, live tunnels); `--explain` includes the egress section.
- Revoke and kill: `--egress-revoke` writes a tombstone and the broker sweeps open tunnels about every second (target two seconds, **[UNVERIFIED]**); `--kill RUN` per section 3; global off switch `AQ_CONFINE_EGRESS=0` or a flag file in the state dir makes every run behave as egress `none`.
- Latency budget: p95 at most 5 ms added at connect, 2 ms per relayed chunk, at least 80% of direct loopback throughput; generation is about 5 tok/s locally (project memory), so streaming overhead is negligible. Budget figures are **[UNVERIFIED]** targets; S2c ships a benchmark that fails at 5x.
- Fail closed: broker cannot start means exit 70 `egress-broker-unavailable` (child never runs), or with `--egress-optional` the run proceeds with egress `none` and records `degraded-none`. Broker dies mid-run: tunnels drop, the run continues without network. Invalid policy or grant files: deny everything. Never any fallback to the host network.
- Profile defaults: `readonly-analysis` and `eval-untrusted` egress `none`, not grantable (guidance still rendered). `worktree-rw`: `none` unless the caller passes `--egress-service`.

## 7A. Remote-lane monitored egress (W2-S7, owner-decided D2)

Owner decision (verbatim): "yes our remote agents are not to be fully quarentined from the internet. they need default access but also monitoring and the system one agent filtered access." This section is the design for that. It is a **monitoring and filtering** layer for processes that are not confined by aq-confine (the Claude and Codex CLI lanes launched through `scripts/ai/delegate-to-claude`, `delegate-to-codex` and the agent loop). It does not make those lanes safe against a hostile agent: a lane with default access can reach any allowed destination. The goals are observation, attribution, deterministic blocking of the clearly bad, and an advisory (later enforceable) judgment on the grey zone.

### 7A.1 Mechanisms evaluated on this host, smallest first
| Option | What it gives | What it cannot do | Cost on this NixOS host |
|---|---|---|---|
| A. `HTTPS_PROXY`/`ALL_PROXY` env pointing at a per-run CONNECT proxy (the S2c-full parser and policy engine run in a **monitor-then-filter mode**) | Hostname-level visibility (the CONNECT target), per-run attribution, deterministic and advisory decisions, per-destination caching | Cannot see traffic from clients that ignore proxy variables (raw sockets, SOCKS-only, tools with their own network stack); opaque TLS inside tunnels | Small: reuses S2c-full code; a per-run loopback listener started by the wrapper; no root |
| B. Per-run systemd scope in a dedicated slice plus an nftables output chain using the `socket cgroupv2` match with counters and logging (declared in NixOS next to the existing `networking.nftables` ruleset in `nix/modules/core/localhost-isolation.nix`) | Catches **every** connection of processes in the scope, including proxy-ignoring CLIs; L3/L4 counters per run; a default log or deny for bypass | Sees addresses and ports only, not hostnames; the kernel log path is rate-limited; processes can leave the scope (same uid can ask the user manager for a new scope) | Medium: root-owned ruleset (owner `nixos-rebuild switch`), wrapper must start lanes with `systemd-run --user --scope --slice=...` ; cgroup matching is **viable on this host**: the reviewer probed `socket cgroupv2` (kernel 7.2.10, nft 1.1.6, `CONFIG_NFT_SOCKET=m`) in a scratch network namespace, including ancestor-level slice matching (`level 4` for a user-created slice: `user.slice`=1, `user-<uid>.slice`=2, `user@<uid>.service`=3, slice=4) and a `udp dport 443` reject; the uid is interpolated from `config.users.users.<owner>.uid` in Nix, never hard-coded. Matching uses the socket's cgroup recorded at creation, so a process moved into the scope later, or a socket passed by fd, keeps its creator's attribution |
| C. Both | A for identity and decisions, B as the bypass detector | | Recommended |

**Honest enforcement model (F1).** Proxy environment variables are **cooperative**: any process in a lane can drop them (`env -u HTTPS_PROXY`, `--noproxy '*'`, `NO_PROXY=*`, raw sockets). Therefore hostname filtering and grey-zone decisions made by the proxy are advisory against a non-cooperating or prompt-injected process **in every mode**, including `enforce`; they are real controls only for cooperating clients. The only non-cooperative control is the cgroup/nft layer (option B), which sees addresses and ports. Consequences, all built into this section: (1) the hostname-free hard-deny set (cloud metadata and link-local `169.254.0.0/16`, IPv6 link-local `fe80::/10`, unspecified addresses, and optionally RFC1918 other than named LAN hosts) is implemented in **nft for the lane slice**, so it holds without the proxy; (2) the stateless bypass definition of 7A.2; (3) S7e's enforcement is defined as "the lane slice may connect directly only to loopback (the proxy); everything else is rejected", which makes the proxy mandatory and gives layer A real force. A transparent redirect of tcp/443 from the slice to the monitor, reading SNI from the ClientHello without TLS interception, would remove the dependence on environment variables; it needs a per-slice listener and peer attribution and is a **follow-up**, not a v1 requirement.

**Recommendation: C, staged.** A gives the hostname-level view and the decision point for cooperating clients; B guarantees that a CLI ignoring the proxy variables is still counted and gives the non-cooperative hard-deny and, at S7e, the enforcement. Bypass handling is the stateless rule of 7A.2.

Facts checked about the lanes (current docs, **[UNVERIFIED]** that they remain current): Claude Code supports `HTTPS_PROXY` (recommended) with `HTTP_PROXY` fallback and `NO_PROXY`; it does **not** support SOCKS proxies; its required hosts are `api.anthropic.com` (API, WebFetch domain check, feature flags, telemetry), `claude.ai` and `claude.com` (authentication and sign-in redirects) and `platform.claude.com` (Console authentication), with `registry.npmjs.org` for npm installs and `storage.googleapis.com` and `downloads.claude.ai` for the native installer ([Claude Code network configuration](https://code.claude.com/docs/en/network-config)). Codex: the workspace-write sandbox has network off by default; when network access is enabled it can start its own loopback network proxy and inject `HTTP_PROXY`/`ALL_PROXY` into subprocesses (reported by secondary sources; its own endpoint list was not found in what I could read) ([Codex agent approvals and security](https://developers.openai.com/codex/agent-approvals-security), secondary: [network proxy write-up](https://codex.danielvaughan.com/2026/06/04/codex-cli-network-proxy-sandboxed-outbound-traffic-domain-policies-socks5-mitm/)).

### 7A.2 Observation, attribution, bypass definition, monitor service
- The wrapper that launches a remote lane (`delegate-to-claude`, `delegate-to-codex`, the agent loop, `aq-ide-launch`) creates a **run label** (lane, role, opaque task id; the label must never contain task text) and starts the lane inside `systemd-run --user --scope --slice=aq-remote-lanes.slice --unit=aq-lane-<run>` (option B), exporting `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` for the monitor with the run label as the proxy user name (an attribution label, not a secret and not authentication). `NO_PROXY` covers loopback so local tool traffic (for example host MCP servers) is not routed through the proxy.
- **Monitor service (F4, F9, F10).** The monitor is a systemd **user service with socket activation** and `Restart=always`, **one long-lived instance per lane class** (not per run), running **outside** the lane slice; per-run attribution is the proxy user name. It binds an ephemeral or option-derived loopback port recorded in a state file (never a hard-coded port), and an nft rule admits connections to that port only from the lane slice and the sampler (mirroring the gid rule in `nix/modules/core/localhost-isolation.nix:36-44`), so it is not a free relay for other local users or processes. It accepts only strict `CONNECT` (same parser as S2c-full: charset and length caps, header limit, no pipelined bytes, plain HTTP gets 405 and a log line), with a try/except around every connection, bounded connection counts, header bytes and idle timeouts. Connections go to the already-checked global addresses with **sequential, happy-eyeballs-style fallback** and short per-address timeouts (an unreachable first IPv6 answer must not stall CONNECT for the full connect timeout); name resolution runs in a thread pool and is cached per name with TTL. The S2c-full parser fuzz tests are a hard acceptance row here.
- **Stateless bypass definition (F2).** Because the monitor runs outside the slice, a proxied connection never originates from the slice: the slice's only legitimate outbound is to loopback. The nft rule for the slice therefore **counts and logs every non-loopback connection** (TCP and UDP), with no address sets and no DNS-keyed updater. Loopback is governed separately by the existing gid rules. A lane that runs its own proxy for its subprocesses (Codex, per secondary sources) puts that proxy inside the slice; its upstream connections would all count as bypass, so either chain it to our monitor through its upstream setting (**[UNVERIFIED]**, tested per lane in S7b) or accept and document `bypass` events for that lane and exclude the lane's own proxy executable by path in the sampler.
- Every proxied connection is logged: time, lane, role, run id, destination host and port, resolved class, decision and its layer (`allow-provider|allow-registry|allow-cached|deny-hard|allow-grey-advised|deny-grey|bypass|bypass-udp|bypass-dns`), bytes each way, duration. A CONNECT tunnel exposes no paths, headers or bodies and none are recorded. Hostnames in logs, alerts and dashboards use the S2c-full escaping rules. Logs go to the telemetry directory as `remote-egress.jsonl` (single appended lines under 4096 bytes, rotation, mode 0600).
- Visibility is per CONNECT, not per request: HTTP/2 clients may coalesce connections across hostnames sharing a certificate, so the monitor sees the first CONNECT host.

### 7A.3 Filter layer
1. **Deterministic hard-deny (cannot be overridden by any learned component), in two places.** (a) **In nft for the lane slice (proxy-independent, F1):** cloud metadata and link-local (`169.254.0.0/16`, `fe80::/10`), unspecified addresses, and optionally RFC1918 other than named LAN hosts; these hold even when the lane drops its proxy variables. (b) **In the monitor, for cooperating clients:** the same set plus loopback and local service ports not granted (checked after name resolution with the global-address rule of 7.4), and a static known-bad list in the repo (`config/remote-lane-egress.json`) with an optional feed from the crowdsec bouncer (`nix/modules/services/crowdsec.nix`, **[UNVERIFIED]** whether its decisions are exportable). Loopback service access by the lanes today is admitted by `nix/modules/core/localhost-isolation.nix` for the primary user's group and is governed by the agent-auth design, not here.
2. **Deterministic allow, per lane** from `config/remote-lane-egress.json` (reviewed in git, edited by PR), **exact hostnames only, no wildcards**, **seeded from vendor documentation only**. Claude: `api.anthropic.com`, `claude.ai`, `claude.com`, `platform.claude.com` (vendor docs, checked). Codex/OpenAI, Antigravity/Google, GitHub and registries: hostnames in section 7A.5 are **[UNVERIFIED]** until confirmed from vendor documentation. Installer hosts such as `storage.googleapis.com` and `downloads.claude.ai` stay **off** the standing allowlist (tenant-shared storage), and GitHub write APIs are a named residual. **Learning week (F7):** observation never writes entries; it produces *proposals* with provenance (number of runs and tasks, first and last seen, whether the run had read untrusted web content), flags single-run entries, and applies a static **never-learn list** (paste and file-sharing hosts, tunnels, dynamic-DNS, raw-IP destinations, bucket/blob-style multi-tenant storage names, anything credential-bearing). First-seen alerts for non-provider destinations are **not** suppressed during learning; they are deduplicated into one daily digest. The owner reviews proposals and merges accepted ones by PR.
   **Auth-critical set (F8):** each lane has a protected set of login and token-refresh hosts (confirmed from vendor documentation; for Claude `claude.ai` and `platform.claude.com`; Google token endpoints for Antigravity/`agy`; ChatGPT login hosts for Codex, all otherwise **[UNVERIFIED]**) that is **never subject to `deny-grey`** in any mode, only to alerts, because a refresh host denied at session expiry would silently log the lane out mid-task.
3. **Grey zone** (not hard-denied, not on the lane's allow list): decided by the **aq-decide** engine (`aq-decide-DESIGN.md`, section 4.5 "Permissions and aq-confine egress": question `egress_grey` with choices `likely_benign_mirror`, `unknown`, `suspicious`; deterministic rules stay authoritative, the engine may only advise, and on abstain or error the stricter path applies). Settings, owner-controlled through one switch `AQ_REMOTE_EGRESS_MODE` (config file plus environment, default `advise`):
   - `monitor`: log only.
   - `advise` (default): the connection is allowed immediately; the decision is requested asynchronously, cached per (lane, host, port) with a TTL, and the verdict is logged; `suspicious` raises a high alert, `unknown` for a never-seen destination raises a medium alert. Nothing is blocked by the engine.
   - `enforce`: after an evidence period (aq-decide asks for at least 14 days or 500 decisions per question in shadow before any promotion, and treats security-class questions as needing a separate owner decision), a `suspicious` verdict denies the CONNECT with the fixed steering reply (7.6); `unknown` follows an owner-set default (allow with alert is the recommended default). Learned models never override the hard-deny layer, the auth-critical set or an allow list. ### 7A.6 IDE and GUI lanes, the sampler, and attribution quality
The Antigravity IDE and any other GUI agent are not started by our wrappers unless we make that the only start path.

**Correction (F1/F2 review, probe-backed).** An earlier text said a random scope suffix cannot be matched by name. That was wrong: `socket cgroupv2` matches an **ancestor** cgroup at a given level, so a slice-level rule (a user-created slice is level 4, uid interpolated in Nix) matches every scope inside the slice without knowing scope names. On this host the desktop (COSMIC) places each GUI app in its own `app-<name>-<id>.scope` under `app.slice`; a rule at the `app.slice` level would cover every GUI app including the browser, so it is useful only as a counter, not as lane attribution.

**Operational requirement (F2).** `aq-antigravity-inbox wake` runs `antigravity chat --reuse-window ...`; for a single-instance Electron app that call hands off over IPC to the **already running** instance and exits, so a wrapper scope around it attributes nothing; all traffic comes from the existing desktop-launched IDE. Scope attribution for the IDE lane therefore **requires the IDE itself to be started inside the slice**: `aq-ide-launch` as the only start path, plus a Nix-declared desktop-entry override so the desktop starts it that way. Without that, only the sampler applies, and the lane table says so. Processes the IDE starts through `systemd-run --user`, D-Bus activation or a desktop portal land outside the slice: a documented gap, counted as `unattributed`.

**Sampler scope and privacy (F5).** A user-level sampler reads established TCP connections (and UDP flows) of the owner uid. It records **destinations only** for: (a) processes in `aq-remote-lanes.slice`, (b) processes whose `exe` realpath matches the lane table, and (c) their process-tree descendants. Every other owner-uid connection is **counted only** (per executable name, no destination, no log line) unless its destination is on the hard-deny list. The sampler **never reads `/proc/<pid>/cmdline` or `environ`** (they carry prompts and tokens passed in argv); a static check and a test enforce this. Retention uses the same rotation as other telemetry, mode 0600. Sampling interval is a couple of seconds, so very short connections can be missed; destination names for non-proxied traffic come from the monitor's recent DNS answers only for clients using the system resolver **[UNVERIFIED]**.

**Attribution quality (F3).** Each event carries `attr: scope | exe | comm`. Order of trust: cgroup/scope membership, then `/proc/<pid>/exe` realpath (store-path prefix per lane), and only then `comm`, a **low-confidence** label because same-uid processes can set it. No per-lane "known provider" suppression applies to `comm`-only attribution, and a `comm`-only event with a non-allowlisted destination is a medium alert. Honest limit: a hostile same-uid process can run any binary under any scope and can create scopes outside the slice through the user manager, so attribution is accountability for cooperating tools, not a boundary.

**Fallback when attribution is impossible:** for the lane-scoped processes in (a)-(c) that cannot be mapped, log as lane `unattributed-owner-session` with destination; for other owner processes only the count exists (privacy), and a rising share of unattributed *lane-scoped* traffic is itself an alert. Events are never silently dropped.

### 7A.7 Credential protection, native sandboxes, failure modes
**OAuth tokens stay where they are.** Each lane's credentials remain in its own store (the CLI's config directory or the IDE's account session). The monitor never reads them, never receives them, and the harness never copies them into the proxy environment. TLS is **not** intercepted: a CONNECT tunnel carries the lane's TLS session end to end, so `Authorization` headers and bodies are invisible to the proxy and to the logs (the proxy sees host and port only). The proxy user name is the non-secret run label. Proxy variables in the lane's environment contain no secret. No lane is configured with a custom CA. Logs carry destinations, byte counts and decisions, never request data. The existing `scripts/ai/claude-api-proxy.py` is deliberately not in the path (it would hold OAuth-bearing requests in a second process).

**Interplay with the lanes' native sandboxes.** Native sandboxes confine what commands a lane may run and, for some, what network those commands may use; they are additional boundaries and stay on as the harness configures them. The monitor must work regardless of them: (1) the cgroup/nft layer and the sampler are independent of any lane's sandbox or proxy settings, which is why option B exists; (2) where a lane starts its own proxy for subprocesses (Codex does so when its network access is enabled, per secondary sources) and overrides the proxy variables for its children, those children may not pass through our proxy, and are then counted as `bypass` or attributed by the sampler; whether our proxy can be chained as that lane's upstream is **[UNVERIFIED]** and is tested per lane in S7b; (3) a lane's own sandbox that blocks network for commands will simply produce no events, which is correct; (4) because these lanes are not hosted in aq-confine, the nested-user-namespace conflict does not arise and `--disable-userns` is unaffected. Per-lane results go into the lane table as they are measured.

**Failure modes (F4).** *At launch:* if the monitor cannot be reached, **fail-open with a high alert**: the lane starts without proxy variables, and the nft counters and sampler still record its traffic; this is the owner's "default access" choice (D4) and a deliberate departure from the fail-closed rule for confined runs. *Mid-run:* the monitor is a socket-activated user service with `Restart=always`, one long-lived instance per lane class, so a restart is seamless and connections queue briefly; resources are bounded and the parser is fuzz-tested (an injected agent must not be able to crash or wedge the service); a crash loop is a high alert. If the monitor is unreachable mid-run, clients configured with the proxy variables fail new connections; this is detected, never silently tolerated: the wrapper alerts, and the documented one-flag rollback is to unset the proxy variables for new lane starts. The nft hard-deny (7A.1) and counters stay in force without the monitor. *Policy errors:* an invalid allowlist or policy file falls back to `monitor` mode (log only) with a high alert, never to a mode that blocks provider traffic; the auth-critical set and the hard-deny layer apply in every mode.

### 7A.8 UDP, QUIC, DoH and DNS (F6)
- **QUIC/HTTP3:** the lane slice gets `udp dport 443 reject` by default (S7c); clients fall back to TCP/443 without functional loss, and a proxy-honoring client does not use QUIC anyway. Other UDP from the slice is counted as `bypass-udp`. The reject rule was probed to act in a scratch namespace.
- **DoH:** a client with DNS-over-HTTPS resolves over 443 to a public resolver, which looks like ordinary HTTPS and removes the monitor's DNS view. A static list of well-known DoH resolver names and addresses raises a `bypass-dns` alert class (cooperating clients through the proxy are checked by name; direct ones by address in nft).
- **DNS exfiltration through the system resolver** (`127.0.0.53`) is invisible to both layers (loopback). Smallest choice: **log queries made by the lane slice** (resolver query logging scoped to the slice, S7a item) and alert on high-entropy or unusually long labels; if that logging is not feasible on this host it is an **accepted residual**, stated with a number: a label carries up to 63 characters and a name up to 253, so a slow trickle can move on the order of a few hundred bytes per query **[UNVERIFIED]** rate in practice.
- **Residuals:** HTTP/2 coalescing (visibility per CONNECT); hostnames can themselves encode data.

### Notes for W2-S3's systemd unit (Rules 13, 14)

### Where the suite runs
The suite starts with the launcher's own preflight. If confinement is unavailable: print `SKIP-WARN: confinement unavailable (<reason>); N behavioral tests skipped`, run the pure tests (argv construction, goldens, path policy, exit codes, schema, static checks, policy-engine unit tests with fake sockets) and exit 0, counting skips. With `AQ_CONFINE_REQUIRE=1` a failed preflight is a hard failure. That variable is set in the dedicated CI job and on the owner host in tier0 (wiring to confirm at implementation, **[UNVERIFIED]**).

### CI investigation and recommendation
Findings:
- Ubuntu restricts unprivileged user namespaces per application via AppArmor: creation is allowed only for processes confined by a profile with a `userns` rule (or with CAP_SYS_ADMIN); controls are `kernel.apparmor_restrict_unprivileged_userns` and `kernel.apparmor_restrict_unprivileged_unconfined`; Ubuntu prefers per-application profiles to disabling the sysctl globally ([Ubuntu blog](https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces)). With the restriction on and no bwrap profile, bwrap fails with `Operation not permitted` or `loopback: Failed RTM_NEWADDR` ([sandbox-runtime #74](https://github.com/anthropic-experimental/sandbox-runtime/issues/74), [opam #5968](https://github.com/ocaml/opam/issues/5968), [melange #1508](https://github.com/chainguard-dev/melange/issues/1508), [opaque #147](https://github.com/opaque-dev/opaque/issues/147)). The apparmor package carries a `bwrap-userns-restrict` extra profile (grants `userns` to bwrap while keeping its children from creating further namespaces); reports say it shipped, was rolled back in 24.04.x because it broke Flatpaks, and is enabled in later releases ([dfaerch/bubblewrap-on-ubuntu](https://github.com/dfaerch/bubblewrap-on-ubuntu)) **[UNVERIFIED]** shipping state on a stock hosted image.
- Not established: whether GitHub-hosted `ubuntu-24.04` has the restriction on by default. Third-party CI configs are ambiguous ([servonaut #195](https://github.com/zb-ss/servonaut/pull/195), [ternly #15](https://github.com/rajasatyajit/ternly/issues/15)); I found no `actions/runner-images` entry. The job therefore probes instead of assuming.
- Repo today: CI uses `ubuntu-latest` (`.github/workflows/tests.yml:14`, `.github/workflows/nix-build.yml:15`), no self-hosted runner, and `nix flake check` is advisory (`nix-build.yml:45`, `|| true`) **[UNVERIFIED line numbers on current main]**. `nixosTest` is not used; VM tests exist only via disko's `makeDiskoTest` in `checks.x86_64-linux` (`flake.nix:380-392`).

| Option | Trade-off | Verdict |
|---|---|---|
| Sysctl off in the job | Weakens only an ephemeral VM, but removes the restriction we want the suite to survive and makes CI unlike production | Acceptable, not preferred |
| Scoped AppArmor profile for the test's bwrap binary, restriction left on | Ubuntu's per-app model; children cannot nest userns, matching `--disable-userns` default; mirrors the W2-S3 production profile | **Recommended** |
| Self-hosted runner on the NixOS box | Highest fidelity but PR code would run next to secrets | Rejected for PR triggers |
| NixOS VM test | Highest fidelity; needs KVM on the runner **[UNVERIFIED]**; flake check is advisory | Later complement |

Recommendation: a dedicated job `confine-tests` with `permissions: contents: read`, own branches and PRs only. Steps: install apt `bubblewrap`; a control check (`unshare --user true` as the unprivileged user, printed, so an unrestricted runner is visible and the test is not vacuous); if the bwrap preflight fails, load the `bwrap-userns-restrict`-style profile for `/usr/bin/bwrap` (copied from the extra-profiles directory if present, else an inline equivalent) with `apparmor_parser -r` and retry; run the suite with `AQ_CONFINE_REQUIRE=1`. The runner has no `/nix/store`, so profiles use the exists-guarded system binds and the preflight uses the host interpreter. If the profile cannot be loaded the job is red by design. Residual: CI proves argv and policy on Ubuntu's kernel; the authoritative gate for NixOS behavior remains tier0 on the owner host.

## S2a implementation notes (deviations from the text above, with reasons)

1. RLIMIT_NPROC is per uid and counts threads; an absolute `nproc` of 256 or 32 makes bwrap fail with EAGAIN on a normal desktop uid (probed: 182 processes). The profile value is therefore headroom above the uid's task count at launch.
2. The worktree admin directory is also a per-run private copy (index and HEAD reflog seeded), bound over the real path, with the read-only `commondir`/`gitdir`/`HEAD` overlays on top. Reason: the sandbox's index and `logs/HEAD` name quarantine-only objects, and a shared admin dir made host `git fsck` and `git gc` fail mid-run (V1 acceptance). After a promoted, clean run the index is copied back only if every object it names exists in the real store and the real index did not change; otherwise it is discarded.
3. Mount order: the `.git` file overlay follows the worktree bind (a later bind would otherwise shadow it).
4. Runs that are killed, time out, hit a size cap or an egress marker never promote refs (killed run leaves real refs untouched); a polluted private ref directory promotes nothing.
5. `git_refs: heads` mode is reserved and rejected at profile load (not part of the S2a acceptance list). `ref-stale` (update-ref old-value mismatch) exits 72 and is reported, never forced.
6. `git commit` inside the sandbox prints a benign `Unable to create packed-refs.lock: Read-only file system` (pseudo-ref cleanup needs the lock in the read-only common dir); exit status and result are unaffected.
7. The CI job (`.github/workflows/confine-tests.yml`) is not part of this change.
8. Review fixes (H1/H2/M1/M3): the sandbox index is never copied back (rebuilt on the host from the promoted tip); protected-path ancestors, socket/FIFO/device-containing subtrees and non-allowlisted `--ro` are refused; scratch is launcher-created (`--scratch`); `--size` bounds on tmpfs and RLIMIT_AS 8 GiB for worktree-rw; run ids are exclusive and worktrees are flocked.
