## Design decisions / contract assumptions (for reviewer attention)
1. **Owner signing key (`--owner-key-path` / `AQ_APPROVAL_OWNER_KEY_PATH`)** is the SERVICE's own
   Ed25519 signing key — the identical `owner_key: bytes` parameter `ApprovalSigner.sign_request`
   has always required (per that module's own docstring: "the owner Ed25519 private key is handed
   in as `owner_key: bytes` by that future service wrapper"). It is **not** the human-factor
   authorization. `sign_request` never signs with it until AFTER a verified, fresh, request-bound,
   user-verified hardware assertion clears every check in the signer — loading the key earlier in
   this CLI's process changes nothing about that gate. No confined UDS service exists yet (P1's own
   deferred activation note), so this CLI plays that not-yet-built service's role in-process, as a
   documented stand-in; a real deployment replaces `--owner-key-path` with the UDS transport the
   design's "hands the assertion back to the signer over the UDS" line anticipates. Tested
   behaviorally: `test_owner_key_alone_never_authorizes_without_an_assertion` proves a genuine
   correct key with no hardware assertion still produces no approval.
2. **FIDO2 CTAP2 PIN** (`_CliUserInteraction.request_pin`, via `getpass`) is the WebAuthn/CTAP2
   standard's own on-device user-verification mechanism — distinct from the passphrase/key-file
   downgrade PRD R2 forbids, since no PIN (correct or not) produces a valid assertion without the
   physical authenticator present. Documented explicitly in the CLI's class docstring to preempt
   reviewer confusion (this is exactly the kind of thing the Antigravity checklist's finding #2
   asks about).
3. **No live request store** (scope fence): `FixtureApprovalStore` is the offline placeholder,
   mirroring P2's own `FixtureApprovalStore`/`configure_store()` seam exactly. A real deployment
   supplies a real `ApprovalStore`.
4. **No declarative udev** (scope fence): documented in `HidrawFido2Client`'s docstring instead —
   a live deployment must add a `services.udev.extraRules` entry declaratively (Rule 13) granting
   hidraw access to the FIDO2 usage page; not shipped here. Until that rule exists,
   `CtapHidDevice.list_devices()` legitimately returns nothing for a non-privileged user, which
   fails closed into `no_key_message` — never a crash (exercised by `test_no_hardware_present_refused`).
5. **`--details` on `list`** shows the Layer-3 drill-in (technical_trail + canonical_hash) as an
   explicit opt-in; the default view is the prep doc's `request_line_format` VERBATIM
   (`"{n}. {title}"`) per line, nothing else — `request_id` is shown on a clearly-secondary indented
   line under `--details` only, needed for `approve`/`deny <request_id>` but never in the default
   Layer-1 view.

verified via the shared `ApprovalSigner` instance, not reimplemented: replay refused identically
(`test_replay_refused_identically_to_browser_path`,

matters (`test_tampered_record_refused_identically`), no-UV / unregistered / revoked credential all

`test_revoked_credential_refused`), no hardware present fails closed
(`test_no_hardware_present_refused`), no passphrase/key-file authorization surface exists
(`test_no_passphrase_or_keyfile_authorization_argument_exists`,
`test_owner_key_alone_never_authorizes_without_an_assertion`), production module excludes any
software/virtual authenticator (`test_production_cli_excludes_software_authenticator`), default
list view is Layer-1 only / `--details` is the only Layer-3 path
(`test_list_default_view_is_layer1_only`, `test_list_details_flag_is_the_only_way_to_see_layer3`).
