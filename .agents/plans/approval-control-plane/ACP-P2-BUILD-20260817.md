# ACP-P2 build record — the approval surface core

Backend route + static approval view for the Approval Control Plane, built to `ACP-P2-DESIGN-20260816.md`
(incl. its "Review fold — Antigravity + local" DOM-isolation/CSP/live-sync/error-mapping/micro-copy folds),
consuming `ACP-PREP-COPY-20260816.md` verbatim (kiosk CSP, error map, "Approvals" card copy). Implemented by
the Claude sonnet lane (Rule 17). Builds against contracts only — no live P1 service, no live request store.

## Files
- `dashboard/backend/api/routes/approvals.py` — FastAPI `APIRouter` (`router`, prefix `/approvals`) with
  `GET /approvals` (Layer-1 pending cards, `response_model` enforced), `GET /approvals/{id}` (Layer-3
  details), `POST /approvals/{id}/challenge` (begins the WebAuthn ceremony via the injected `SignerClient`),
  `POST /approvals/{id}/approve` (request_id + browser assertion only — `extra='forbid'` rejects any
  smuggled bytes/hash field), `POST /approvals/{id}/deny` (no assertion). Second router `view_router` serves
  `GET /approve` with the verbatim kiosk CSP header. `ApprovalStore`/`SignerClient` are `typing.Protocol`
  injected interfaces; `FixtureApprovalStore`/`FixtureSignerClient` are the offline defaults (golden fixtures
  adapted to the two runbooks actually registered in `approval_request.RUNBOOK_REGISTRY`). **Not wired into
  `dashboard/backend/api/main.py`** — `app.include_router(...)` for both routers is deployment-layer, default-OFF.
- `dashboard/backend/static/approve.html` — self-contained HTML/CSS/JS approval view: plain-language cards
  (title/what/why/impact chip/reversible marker), Approve/Deny with the verbatim micro-copy under Approve,
  Details drill-in, polling-based Live-Sync indicator that disables Approve/Deny on a dropped connection,
  the verbatim plain-language error map, `navigator.credentials.get()` WebAuthn call guarded for absence,
  WCAG-AA-oriented controls (native `<button>`s, `:focus-visible`, `prefers-reduced-motion`, ARIA labels,
  light/dark contrast-aware CSS custom properties). Kiosk launch requirement documented in the file's header
  comment, not built (systemd/Nix unit is a separate deployment slice).
- `scripts/testing/test-approval-surface.py` — 22 checks, dual-mode (main + pytest), mounts only the two
  approvals routers in a throwaway `FastAPI()` app (never imports the full `api.main`).

## Contract assumptions / scope decisions (for the reviewer + any resume)
1. **Golden fixtures adapted, not verbatim.** The prep doc's golden fixtures use runbook names
   (`epoch-revoke`, `emit-grant`) that are NOT registered in `approval_request.RUNBOOK_REGISTRY` (only
   `activate-signer-service` and `restart-service` exist). `FixtureApprovalStore` uses the two real runbooks
   instead — adding new runbooks is P0/P3 registry scope, out of P2. Consequence: the fixture set currently
   spans only low/medium impact, both reversible; a high/irreversible fixture needs a P0/P3 registry addition.
2. **No live real-crypto HTTP round-trip test.** `FixtureSignerClient` is a deterministic stand-in
   (`assertion["_outcome"]` selects the outcome), not a real `fido2`-backed adapter — building a full
   browser-JSON↔`fido2.webauthn.AuthenticationResponse` marshalling layer is P1-adapter/deployment work, out
   of P2's scope fence ("no P1 service internals"). The underlying real-crypto contract is already proven by
   P1's own 20/20 test suite (`test-approval-signer.py`); P2's tests instead prove the ROUTE never smuggles
   bytes/hash/keys and correctly delegates via the `SignerClient` protocol (spy-instrumented).
3. **Live-Sync is polling, not a WebSocket.** The task explicitly scoped P2 as "NOT a live socket/service";
   the view polls `GET /api/approvals` every 5s and disables Approve/Deny on any non-2xx/network failure.
4. **"running" is a client-side transient state**, not a P0-persisted status (P0's `STATUSES` has no
   `running` value) — shown optimistically between a successful `/approve` and the record's own transition to
   `executed` (rendered "Done"). This is documented in `approve.html`'s `STATUS_LABELS` comment and matches
   the design's "Approved → running → done" narrative without inventing a new persisted status P0 doesn't have.
5. **AA contrast palette is a good-faith design choice, not machine-verified.** No automated contrast-ratio
   checker was run against the light/dark CSS custom properties; the pairs were chosen to be comfortably
   AA-range but this should be spot-checked with a real contrast tool before kiosk activation.
6. **`dashboard/backend/api/main.py` is untouched** (verified via `git status --short`), per the explicit
   "add an APIRouter module, do NOT rewire the app" instruction. Wiring `app.include_router(approvals.router,
   prefix="/api")` + `app.include_router(approvals.view_router)`, the confined kiosk systemd/Nix unit, and a
   real live `ApprovalStore`/`SignerClient` are the deployment-layer follow-up, default-OFF until then.
