## Success measure (owner-agreed 2026-10-29)

The goal is an accurate board, not a green one. A board that ends "mostly ACTIVATED" would be a warning sign. ## MVP boundary (rev4)

**Hard prerequisite: the sudo owner-boundary slice (branch `fix/sudo-owner-boundary`, owner decision 2026-10-29).** It removes NOPASSWD from `nixos-rebuild`, `systemctl *`, `journalctl *` and the two checkout scripts, lowers `timestamp_timeout` (currently 60 minutes at `nix/modules/core/base.nix:377`), and replaces unattended needs with narrow store-path rules. Signing work does not start until that slice is merged, deployed and its effective-authority audit (item 3, "Owner boundary") passes on the running system. Without it, an agent running as the owner's OS user can run the signer's privileged path with a cached or passwordless credential and the signature means nothing.

First implementation after the prerequisite is bounded to: (a) the owner-controlled verifier and signer deployment, including the effective-authority audit, the root-only key and the safe signer transaction (item 3), (b) the signed envelope, the evidence baseline and per-item revocation state, (c) removal of every unsigned ACTIVATED path in one projection function, (d) the `aq-activation-request` tool, (e) one real item round trip. The effective-authority audit, safe signer transactions, readable head checkpoint and evidence-invalidation contract are inside the MVP and are not deferrable. Deferred until the round trip passes, with reasons:
- **Items outside the signed system closure (rev6).** The MVP can ACTIVATE only items whose implementation and relevant configuration are fully inside the signed system closure: Nix-store code and Nix-generated config, run from the store. Items that execute checkout-backed code, read mutable config (files outside the store that change without a rebuild), or live only in home-manager are REFUSED by the signer. The refusal reason is written in the request and shown to the owner; the item stays SHIPPED and cannot be ACTIVATED.
  - **Eligibility enforcement (rev7).** Eligibility comes ONLY from an owner-controlled store manifest: the Nix option `mySystem.activation.eligibleItems`, declared in the tracked config. For each eligible item it lists the plan/item id, the exact store paths of its executable(s), helpers and configuration, the systemd unit(s), and any mutable state paths the item reads. Nix generates `/etc/aq-activation/eligible.json` (a store-backed symlink) from it; it changes only through a rebuild, which needs the owner's freshly typed password (`timestamp_timeout=0`). The signer reads only that file and ignores any eligibility claim in the request or the tracker. The signer also inspects each listed unit's `ExecStart`, `ExecStartPre`, `Environment`, `EnvironmentFile` and `ReadOnlyPaths`: every path must be in the manifest or the Nix store, and none may be under `/home`, the checkout or a mutable config path. Anything else, and any dependency the signer cannot classify, is refused. At signing the signer prints the manifest entry it is relying on, and the owner confirms it together with the declared state paths.
  - Honest limit: a Nix-store binary can still read mutable state at runtime that this static check cannot see. The manifest entry must declare every state path the item reads, and the owner confirms them at signing. Items with undeclared mutable inputs are out of MVP. Editing the Nix declaration is something an agent can do, but it takes effect only after an owner-authenticated rebuild, and the signer shows the entry at signing time, so the owner sees what an edit changed.
  - Deferred class "external-identity items": activating them needs authenticated identity for what they run and read (for checkout code, a signed commit/tree hash checked at runtime; for mutable config, the file digests in the baseline and re-hashed by the verifier; for home-manager, the generation path in the baseline). Not designed here.
- P0.9 SHIPPED reclassification (item 5): changes the board for 143 items; unsafe before the grant path is proven.
- `aq-activation-sweep` and bulk waves beyond the first (item 6): wave signing is built in (b) only as the manifest format and state machine; bulk use waits for the round trip.
- ACP WebAuthn signer: not shipped yet; the interim sudo signer is the MVP path, and this deferral is acceptable only because the interim boundary is demonstrated by the audit tests.

## Activation now vs. after signing

Owner priority: SHIPPED items should reach ACTIVATED soon. Signing is the only thing that gates the label, so everything else proceeds in parallel now:
- **Proceeds now, no dependency on signing:** per-item triage (item 0: activate, defer or archive), feature-flag flips and rebuild requests for low-risk items, wiring missing callers, guarded enables for high-risk items, running real-world validation, collecting enable evidence and detection signals, independent review, and drafting attestations. Each of these is useful on its own and counts toward the Definition of Done evidence.
- **Waits for signing:** only the ACTIVATED label. Until a verified grant exists, an item whose work is done shows SHIPPED with its evidence ready ("awaiting grant"), and the board counts these separately so the backlog of grant-ready items is visible.
- **Why not signed earlier:** a weaker interim signature would reintroduce the forgery class the pipeline exists to remove, and a grant signed under a cached or passwordless sudo cannot be told from an agent's. Evidence collected now is bound to `system_closure` and re-checked at signing (item 4); if the closure changed at all, the evidence is re-run, not trusted.
- **Order of landing:** sudo owner-boundary slice, then signer MVP, then first-item round trip, then waves of grant-ready items signed in batches by the owner.

## Design

0. **Triage before evidence (per plan wave)**
   - Before any attestation work, each SHIPPED item in the wave gets one decision: activate, defer or archive. Activation is not the default.
   - Agents propose the decision with reasons: live caller, resource cost, overlap with another feature, owner value. The owner confirms or changes it in one batch per wave.
   - Activate: proceeds to step 1. Defer: dated reason recorded in the tracker editorial and the issues backlog. Archive: Rule 12 move plus tracker editorial, only with a parity equivalent or a written reason (P4.3 "wire+activate or archive").
   - Defer and archive are terminal states, never a substitute for ACTIVATED. An editorial defer/archive edit changes the item's status to DEFERRED/ARCHIVED only; it can never produce ACTIVATED, and the projector rejects an item that has both a deferral and an activation claim.
   - Risk tier per item. **Low**: read-only or advisory, easy to turn off. Follows enable → rebuild → validate → review directly. **High**: enforces security, acts autonomously, changes power/sleep/network state, or writes durable state. Gets a guarded enable first, in the `aqosvm` VM configuration or behind `aq-activation-guard` (auto-revert unless confirmed healthy), and only then the production enable.

1. **Activation request (agent side): `scripts/ai/aq-activation-request <plan> <item-id> --attestation <file>`**
   - Parses the attestation in the DoD format. Refuses unless all six dimensions are present and each is evidence or `deferred: <reason>, <YYYY-MM-DD>`; any `MISSING:` refuses. Syntactic completeness is only the filter. At signing (item 2) the owner reviews each dimension's evidence and each dated deferral; the signer shows them one by one and the signature covers the digest of what was shown.
   - Requires the item's `detection.activation_subject` (convention `<plan>:<item-id>`); refuses if absent.
   - Binds the evidence to the deployed system, not to git ancestry. The attestation records: `system_closure` (the `/run/current-system` store path, from `readlink -f`), `config_revision` (`nixos-version --configuration-revision`, required clean), `enable_evidence` (the evaluated option value read from the running system, for example `nixos-option` output or the unit's `systemctl show` on the deployed closure, not a commit hash), `detection_snapshot` (the item's `detection` signals as canonical JSON, captured at request time), `validation_digest` (sha256 of the stored validation output), and `review_digest`. The deployed closure comes from `scripts/maintenance/aq-deploy-current` (branch `feat/deploy-current`, commit `5c5c5055`; PR pending), the step that makes "running system == origin/main commit". This doc depends on that script only for the claim "running == origin/main"; closure acquisition itself is self-contained (`readlink -f /run/current-system` plus `nixos-version --configuration-revision`), so the MVP does not block on the PR, and the exact script subject is cited here so reviewers can inspect it.
   - **Evidence baseline.** The signed envelope carries `evidence_baseline_sha256` (hash of the canonical JSON of `system_closure`, `enable_evidence`, `detection_snapshot`, `validation_digest`, `review_digest`) so the baseline is authenticated by the signature, not inferred from the attestation file. There is no per-item "relevant change" fingerprint in the MVP (see item 4).
   - **Ordering and authenticity of validation artifacts.** Tool-generated timestamps in agent-writable files prove nothing, so ordering is not taken from them. The owner-side signer instead authenticates ordering by content binding: the review artifact embeds `validation_digest` and `system_closure`; the validation artifact embeds `system_closure`; the request embeds `review_digest`. The signer recomputes every digest from the stored bytes at signing time (from the single captured snapshot in item 3), checks each embedded reference against the recomputed value, and shows the owner the artifacts' digests and these links. A validation that does not reference the closure, or a review that does not reference the validation digest it reviewed, refuses. The owner's signature is then the explicit acceptance of those artifacts as the evidence; no code path treats a timestamp or a reviewer name inside them as authenticated.
   - Requires a final-review verdict (PASS or PASS_WITH_FOLLOWUPS) from a lane other than the author. The reviewer identity written in the file is a claim, not proof: the owner signing step shows who reviewed and the review log path, and signing is the owner's explicit acceptance of that review evidence. No code path treats the file's reviewer field as authenticated.
   - Copies the attestation to `.agents/activation/attestations/<plan>/<item-id>-<sha12>.md` and files a human-gate alert through the existing attention queue with `executor: "activation_grant"` and payload `{plan, item_id, subject, attestation_path, attestation_sha256}`.
2. **Owner grant (owner side)**
   - The request appears in the numbered `aq-approve` list as usual. Approving it runs the signing step in item 3; `aq-approve` alone never writes a grant.
   - Before signing: re-hash the attestation (mismatch fails), re-run the completeness check, re-read `/run/current-system` and refuse if it differs from the attested closure, and show subject, item, closure, reviewer claim and the full attestation text.
   - Output: a signed envelope (item 3) written to the root-owned log. The `agent` field is not trusted for anything.
3. **Trust anchor: an owner signature verified by owner-controlled code (revised after Codex review)**
   - Agents, Codex and the owner all run as the same OS user, so OS identity and file permissions cannot tell them apart. The one act agents cannot perform here is `sudo` (owner act), and the one location they cannot write is the Nix store / root-owned paths. The trust anchor must live only in those two places.
   - **Verifier deployment.** The projector, the verifier module, the public-key allowlist and the signer are installed by NixOS as a store path (`environment.systemPackages` entry `aq-activation-verify`, built from the repo at rebuild time). `aq-pm-tracker` and the dashboard backend call the installed verifier by absolute store path (wired in Nix, not discovered). Requirements:
     - The allowlist is a Nix-evaluated file in the store (`/nix/store/...-activation-grant-signers.json`), generated from an option in `nix/modules/` (public keys only). The tracked `config/activation-grant-signers.json` is removed from the trust path. Changing keys requires a rebuild, which is an owner act.
     - The verifier takes no key, allowlist, module or path from the environment, CLI flags, `PYTHONPATH`, `sys.path` inserts or the repo checkout. It runs `python -I` with a fixed interpreter and imports only store-path modules. The checkout's copy of the projector may still render the board for dev use, but any status it computes from checkout code is marked `unverified-checkout` and cannot show ACTIVATED.
     - A deployed-vs-checkout hash check (`aq-activation-verify --self-hash`) is a health-spider probe; mismatch is an alert, not a trust input.
   - **Owner boundary (hard prerequisite, rev4).** A TTY and a typed confirmation are producible by an agent, so they are not a boundary. The boundary is a fresh sudo password that only the owner types. Rev3's assumption that agents cannot sudo was a declaration, not a measurement: `nix/modules/core/base.nix:377` sets a 60-minute credential cache and `nix/modules/host-classes/p14s-amd-ai-workstation.nix:119-127` declares passwordless rebuild, deploy and systemctl commands for the primary user. Requirements:
     - The `fix/sudo-owner-boundary` slice is merged and deployed first (see MVP boundary). It removes NOPASSWD from `nixos-rebuild`, `systemctl *`, `journalctl *` and the two checkout scripts, lowers `timestamp_timeout`, and gives unattended jobs narrow store-path rules only.
     - **No sudo credential caching (owner decision 2026-10-29, rev6).** `Defaults timestamp_timeout=0` globally (added by `fix/sudo-owner-boundary`): every sudo invocation needs a freshly typed password, so no ticket exists for an agent sharing the owner's terminal to reuse. This replaces rev5's tty-isolation argument, which could not rule out an agent with the owner's controlling terminal.
     - **Every remaining NOPASSWD rule is enumerated** in `docs/harness-first/evidence/2026-10-29-sudo-owner-boundary.md` (branch `fix/sudo-owner-boundary`), each with a demonstration that it cannot reach activation authority: write `/var/lib/aq-activation`, change Nix trust config, or run agent-editable code as root through arguments, subprocesses or writable inputs. A rule with no such demonstration is removed. The live audit below fails if `sudo -l` shows any rule not in that table.
     - **Effective-authority audit** (a script run on the live system, output pasted into the PR and re-run by a health-spider probe): (1) `sudo -l` for the primary user, parsed, must show no NOPASSWD entry that can reach root-owned state, the signer key, `/var/lib/aq-activation` or an arbitrary command; (2) `sudo -n true` and `sudo -n <each remaining allowed command>` must fail without a password; (3) effective `timestamp_timeout` is 0 globally (from `sudo -V` / `sudoers` evaluation); (3b) `sudo -l` matches the enumerated table above; (4) SOPS decryption authority: the age key `~/.config/sops/age/keys.txt` (declared around line 107 of the same host-class file) is user-readable, so anything encrypted to that key is readable by any agent. The audit lists every secret decryptable with it. The activation signing key must not be one of them.
   - **Key storage (revised).** The signing key is NOT a SOPS secret. It is generated on the host by the signer's first-run bootstrap (`sudo aq-activation-sign --init-key`, owner act): an Ed25519 key written to `/var/lib/aq-activation/signing.key`, `root:root 0400`, parent directory `root:root 0755` declared via `systemd.tmpfiles.rules`. It is never in the repo, never in `secrets.nix`, never encrypted to the user age key, and never copied by `aq-provision-signer-key`. Only the public key leaves the host: the owner adds it to the Nix-evaluated allowlist (rebuild, item 3 "Verifier deployment"). Audit before enabling: list every service with `LoadCredential`/`ReadOnlyPaths`/`BindPaths` that could expose `/var/lib/aq-activation`; none may be granted. Loss of the key is handled by generating a new key and a rebuild that rotates the allowlist; old grants verified against the old key remain valid only if the old public key stays in the allowlist (owner decision at rotation).
   - **Signer execution.** `sudo aq-activation-sign <request_id>` resolves to the installed store-path binary; sudoers is declared in Nix with `Defaults!/run/current-system/sw/bin/aq-activation-sign env_reset` and a command spec that allows exactly that binary with exactly one argument. The signer runs with a scrubbed environment (`python -I`, no inherited `PYTHON*`, `PATH` fixed), reads only the store-path code, and reads request data as inert bytes (never imports or executes anything from the checkout). It requires an interactive TTY and a typed confirmation as friction for the owner; the authentication is the fresh password above. There is no noninteractive or stdin-driven mode. Target replacement: the Approval Control Plane signer (`scripts/ai/lib/approval_signer.py`, WebAuthn tap) when its service and CLI ship; it uses the same envelope and verifier.
   - **Signer file safety and transaction.** The root signer reads files an agent controls, so:
     - `request_id` is bounded: `^[a-z0-9]{8,40}$`, length checked before any path join, never used as a path component without that check; plan and item ids from the request must match the tracker pattern `^[a-z0-9._-]{1,64}$`.
     - Files are opened with `openat` relative to a directory file descriptor opened once, `O_NOFOLLOW|O_CLOEXEC`, regular files only (`fstat` after open), size capped; no path is resolved twice, so a symlink or directory swap between check and open is not followed.
     - One captured snapshot: the signer reads the request, attestation and the validation/review artifacts once into memory, hashes them, and uses those same bytes for the completeness check, the owner display and the signed digests. Nothing is re-read after display. The signer also writes those exact bytes to a root-owned evidence copy `/var/lib/aq-activation/evidence/<seq>/` (same ownership and mode as the log), listed by name and digest in the segment; the verifier rehashes this copy, never the agent-writable originals.
     - Coverage check at signing: the signer refuses (reason in the request) any item whose implementation or relevant config is not fully in the signed system closure (see MVP boundary). A change on disk after capture is irrelevant to this signature and caught by the verifier's later hash check.
     - Exclusive lock: `flock(LOCK_EX)` on `/var/lib/aq-activation/lock` (root-owned) is held from reading the head through updating it. Concurrent grant/revoke calls serialize; a second signer waits or fails, never interleaves.
     - Durable ordering: (1) write the new envelope to the log directory's root-owned segment file `/var/lib/aq-activation/log/<seq>.json` (create exclusive, `fsync` file, `fsync` directory), (2) write the new head checkpoint to a temp file and `rename` over `head`, `fsync` file and directory. The signer then exits. It writes nothing into the checkout, ever. The verifier and projector read the world-readable root-owned segments and head directly. If a checkout copy of the log is wanted for browsing, the unprivileged CLI writes it after the signer exits; the verifier never reads it and a failure to write it affects nothing.
     - Fail-closed recovery: on start the signer and the verifier compare the highest segment to the head. Segment `seq` equal to head `seq` + 1 with `prev_hash` matching the head means a crash between steps 1 and 2: the signer completes the head update after validating the segment's signature; the verifier treats the pending state as not yet granted (no ACTIVATED from an unfinalized segment) and raises an alert. Rev7: any head/segment mismatch, including a persisted segment beyond the head (an unfinalized write, which could be a revoke), blocks ALL ACTIVATED projection for every item until owner recovery (`--recover` or the next signer run completing the head) finishes. This fails closed globally, not per item, so a previously granted item cannot keep projecting ACTIVATED while a revoke awaits finalization. Any other gap, hole, duplicate `seq`, or hash mismatch makes the verifier fail closed for all items until the owner repairs it under sudo.
   - **Signed envelope** (versioned, domain-separated). Signed bytes are the canonical JSON (sorted keys, UTF-8, no whitespace) of:
     `{v: 1, domain: "nixos-dev-quick-deploy/activation/v1", op: "grant"|"revoke"|"wave-grant", deployment_id, plan, item_id, subject, attestation_sha256, system_closure, evidence_baseline_sha256, approver, ts, request_id, seq, prev_hash}`
     - `domain` is a fixed prefix; the signature input is `domain || 0x00 || canonical_json`, so a signature cannot be reused for any other message type or tool.
     - `op` is inside the signed bytes, so a revoke cannot be relabeled as a grant. The verifier dispatches on the signed `op`, never on an unsigned field.
     - `deployment_id` is derived from the machine (a Nix-declared value, `/etc/machine-id` hash) so another machine's grants do not verify here.
     - Full item identity is `(plan, item_id, subject)` plus the attestation hash; all four must match the current tracker item or the grant does not apply.
   - **Anti-replay and revoke protection.** Every signed envelope carries `seq` (monotonic per deployment) and `prev_hash` (hash of the previous envelope, a chain). The owner-side head `(seq, hash)` is a checkpoint file `/var/lib/aq-activation/head`, owned `root:root`, mode `0644` (world-readable), in a `root:root 0755` directory declared via `systemd.tmpfiles.rules`; only the signer, under sudo, writes it. The verifier runs as the unprivileged caller and only reads it, so no privileged reader service is needed; the file is integrity-protected by its location (agents cannot write there) and its content is cross-checked against the signed log. The chain segments in `/var/lib/aq-activation/log/` have the same ownership and mode. The verifier requires the segments to chain from the first envelope to a head that matches; a deleted revoke, a missing tail, an inserted replay or a reordered older grant breaks the chain or falls behind `seq` and fails closed (item 4). Unsigned timestamps and append order carry no authority; only `seq`/`prev_hash` under a valid signature do.
   - **Bootstrap and missing state.** The genesis is an explicit owner act: `sudo aq-activation-sign --init-chain` writes segment 0 (signed, `op: "genesis"`, carrying `deployment_id`) and the head together, and refuses if `/var/lib/aq-activation/log/` already holds any segment or the head exists. An absent head with existing segments, an absent segment directory with an existing head, an unreadable or malformed head, or a head whose hash does not match its segment is a corrupted state: the verifier fails closed for every item and alerts, and the signer refuses to sign or re-init over it. The signer never recreates a missing head from the log without an explicit owner-run `--recover` that revalidates every signature and shows the result. No state ever permits reinitialization over existing history.
   - **Waves.** The owner signs once per reviewed wave, but the wave is an `op: "wave-grant"` envelope whose signed bytes include `wave_id` and the complete sorted list of `{plan, item_id, subject, attestation_sha256, system_closure, evidence_baseline_sha256}` tuples. Rules: no duplicate `(plan, item_id)` or `subject`; the verifier counts an item granted by a wave only if its exact tuple is in the signed list (membership cannot be fabricated outside the signed bytes); an item's current attestation hash must equal the listed one.
   - **Per-item state machine.** The verifier folds the chain in `seq` order into one state per item key `(plan, item_id, subject)`: `none -> granted` (individual `grant`, or `wave-grant` containing the item) and `granted -> revoked` (individual `revoke`). Transition rules: a `revoke` sets `revoked` from any state; in `revoked`, a `wave-grant` is ignored (it cannot clear a revoke, whatever its `seq`, even higher than the revoke's); only a later individual `grant` for that item (higher `seq` than the revoke, valid attestation) moves `revoked -> granted`. A `wave-grant` or `grant` while already `granted` only replaces the baseline. ACTIVATED requires final state `granted`; this is the single definition, item 4 uses it.
4. **Single activation path in the projector (P0.7)**
   - One function, `activation_verified(plan, item_id, subject, attestation_path) -> bool`, in the store-installed verifier. It is the only code that may cause ACTIVATED. Both projectors call it: `_activation_events` in `refactor_status.py` and the grant/ACTIVATED branches of `aq-pm-tracker::project_item`. A grant counts only if: the chain verifies against the root-owned head, the signature verifies against the store allowlist, `op` and identity match, the item's final state in the per-item state machine (item 3) is `granted`, the attestation file still hashes to the signed hash, the deployed system closure still equals the signed `system_closure` (staleness rule below), and the evidence baseline recomputes: the verifier resolves each validation/review artifact named in the segment to the root-owned evidence copy (item 3), rehashes it, recomputes `evidence_baseline_sha256` from the recomputed `validation_digest` and `review_digest` plus the signed `system_closure`, `enable_evidence` and `detection_snapshot`, and compares with the signed value. A missing, unreadable or mismatching artifact, or a baseline mismatch, fails closed (not ACTIVATED; shown `activation_stale`).
   - Unsigned bypasses removed in the same change (verified locations in the current file):
     - `project_item` line 473: delete the `accepted and (pct is None or pct == 100)` alternative. An `is_activation` item becomes ACTIVATED only through `activation_verified`. `acceptance.status` still gates SHIPPED (`_gate`), never ACTIVATED.
     - Lines 445/449: before returning `_project_systemd`/`_project_command`, the function computes `verified = activation_verified(...)` for items with an `activation_subject`; ACTIVATED is returned when it is true and the live ground-truth check also passes, otherwise the existing result. ACTIVATED is therefore reachable for service and tool items, but only through the verified path.
     - Lines 474-476: a verified grant yields ACTIVATED for any kind and phase (rev2 left most verified grants at SHIPPED). An unverified claim of any kind yields no change and counts as `grants_unverified`.
     - `_aq_grants` and the `f"activation.grant {subj}" in grants` substring match are deleted; there is no second reader.
   - Acceptance test (below) greps the projector for any `"ACTIVATED"` result that does not pass through `activation_verified`.
   - **Evidence validity over time (MVP: any closure change stales the grant).** The grant is bound to the signed `system_closure` and `evidence_baseline_sha256`. Only items fully inside the system closure can be granted (MVP boundary), so any change of the deployed system closure (`readlink -f /run/current-system` differs from the signed value) marks the grant `grant-stale`. Changes outside the closure (checkout code, mutable config) cannot stale a grant because items depending on them were refused at signing and can never be ACTIVATED. A stale item shows SHIPPED with `activation_stale`, not ACTIVATED, and needs fresh validation, fresh independent review and a fresh signature. There is no per-item carry-forward in the MVP: nothing is inferred about which changes were "relevant", so an imported helper, config file or runtime dependency changing can never leave a grant standing. The attestation hash must also be unchanged. If the closure cannot be read, the grant is stale.
   - **Operational cost.** Every rebuild stales every grant, so ACTIVATED labels hold only between rebuilds. Mitigation is batching, not a weaker rule: re-validate and re-sign the affected items as one wave (signed waves, item 3) after a rebuild, and rebuild less often. Accepted for the MVP because an inaccurate ACTIVATED is worse than a temporarily SHIPPED board (see Success measure).
   - **Deferred enhancement: dependency-aware carry-forward.** Carrying a grant across closures needs an authoritative dependency-coverage rule (imports, helper executables, config) that fails closed when coverage is unknown. Acceptance gate before it can ship: change an imported helper while the entry point, unit state and enable evidence stay identical, and the grant must go stale.
   - Unsigned or failed-verification grants are ignored and counted as `grants_unverified` on the board.
   - Items without `detection.activation_subject` stay unactivatable until the subject is added to their tracker editorial (a PR). The board shows the count.
5. **SHIPPED needs an activation signal (P0.9)** — deferred (see MVP boundary).
   - Already designed in DESIGN.md: SHIPPED requires a wired caller, enabled unit or live check plus a registered test; otherwise BUILT. Implemented after 1-4 and the round trip so the board does not drop before the grant path exists.
6. **Evidence at scale (P2.3 / P4.3)** — deferred past the first round trip.
   - `aq-activation-sweep <plan>` drafts attestations: for items with `systemd_unit`/`command` detection it records live `systemctl show` / command output for dimensions 2-3; the rest get `MISSING:` lines to fill. Drafts are inputs to step 1, never grants.
   - Waves by plan, smallest blast radius first: AQ-OS Tools (15), Services (23), Capabilities (9), then the recovery plan.

## Acceptance tests

- A hand-appended `{"type":"activation.grant","agent":"owner",...}` line, with or without a forged approved alert in the attention archive, does not change any item's status (no valid signature).
- Local key substitution: an agent generates its own keypair, edits the checkout's allowlist, sets `PYTHONPATH`/env overrides and signs a grant. The installed verifier still rejects it, and the checkout projector shows `unverified-checkout`, never ACTIVATED.
- Setting `acceptance.status: "accepted"` on an `is_activation` item, on a `systemd_unit` item and on a `command` item leaves none ACTIVATED.
- A verified grant on a non-owner-act item in a non-"activation" phase projects ACTIVATED (not SHIPPED).
- Relabeling a signed revoke as a grant (changing the unsigned `type`) fails; `op` is read only from signed bytes.
- Deleting a signed revoke from the log, truncating the log tail, or replaying an older grant fails the chain/head check and the verifier fails closed (no ACTIVATED).
- Replacing an attestation file after signing voids that grant. Any change of the deployed system closure (even an unrelated module) marks it `grant-stale`.
- Forged wave manifest (item not in the signed list), duplicate entries, tampered tuple: rejected. Partial revoke of one wave item, then replay of the whole wave: the revoked item stays revoked, the others stay granted.
- Signer: runs only from the store path; with a planted `json.py`/`sitecustomize.py` in the checkout and in `PYTHONPATH`, the key is not exposed; no noninteractive invocation signs.
- Two valid grants for one subject project once; a later higher-`seq` revoke wins.
- Approving a request whose attestation was edited after filing fails and writes no grant.
- An attestation with any `MISSING:` cannot be filed. A deferral entry without a date or reason cannot be filed.
- Shared terminal (rev6): after the owner authenticates any sudo command in terminal A, an agent process sharing terminal A gets a password prompt (or `sudo -n` fails) for the signer and for every root-capable command.
- Eligibility manifest (rev7): an agent editing the request or tracker cannot make an item eligible; an item absent from `/etc/aq-activation/eligible.json` is refused; a unit whose ExecStart/ExecStartPre/Environment/EnvironmentFile/ReadOnlyPaths references a checkout, `/home` or mutable config path is refused; an unclassifiable dependency is refused; the signer displays the manifest entry relied on.
- Pending revoke (rev7): kill the signer after persisting a revoke segment but before the head update; the previously granted item, and every other item, stops projecting ACTIVATED until `--recover` completes.
- Coverage refusal (rev6): change a checkout-backed helper or a mutable config file read by an item without a rebuild; the item was refused at signing (so cannot be ACTIVATED). A home-manager-only item is likewise refused.
- Owner boundary (all run on the live system after the sudo slice): with `timestamp_timeout=0`, from a process with no tty, from tty B and from the owner's own tty, every privileged path (the signer, each remaining NOPASSWD command, `nixos-rebuild`, `systemctl`) fails to reach activation authority (no write to `/var/lib/aq-activation`, no change to Nix trust config, no root execution of agent-editable code); `sudo -l` matches the enumerated evidence table; direct decryption (`sops -d` / `age -d` with `~/.config/sops/age/keys.txt` over every tracked secret) never yields the activation signing key; the key file is `root:root 0400` and unreadable by the primary user.
- Evidence baseline: change an imported helper with entry point and enable/unit state identical, rebuild: grant goes `grant-stale`. Change only an unrelated module, rebuild: grant also goes stale (MVP rule). Re-sign as one wave: grants return. Edit validation or review artifacts after signing: the verifier rehashes the root-owned evidence copy and the baseline recomputes; editing the originals changes nothing, and deleting or corrupting the copy fails closed (not ACTIVATED). A validation artifact naming a different closure, or a review that does not embed the validation digest, is refused at signing.
- Signer safety: `request_id` with `../`, absolute paths, overlong or non-pattern values is refused; a symlink swapped in for the request or attestation between request and signing is not followed (`O_NOFOLLOW`); the attestation changed on disk after the owner display does not alter the bytes signed (signature covers the captured snapshot); two concurrent grant/revoke runs serialize with distinct `seq` and an intact chain; kill the signer after the segment is durable but before the head rename: the verifier shows no ACTIVATED from the pending segment and alerts, the next signer run completes the head, and no state signs a duplicate `seq`; the signer creates no file under the checkout (strace/inotify shows no checkout writes), and a hostile symlink or hard link planted in the checkout has no effect.
- Head checkpoint: unprivileged verifier reads head and segments (0644 in a 0755 root dir); head deleted with segments present, segments deleted with head present, head unreadable, head corrupted, and each of these after a restart: verifier fails closed for all items and `--init-chain` refuses; only `--recover` (owner, revalidating all signatures) repairs it.
- Revoke state machine: sign grant, revoke, then a newly signed higher-`seq` wave containing the item: item stays revoked; then an individual regrant with higher `seq`: item is granted. Replaying an old wave alone is tested separately and also stays revoked.
- A full round trip (request → owner approve via sudo signer → installed verifier → projector shows ACTIVATED) works for one real item end to end, on the deployed system.

## Rollback

Each build step is additive, but rollback never restores trust in self-asserted grants. Two allowed rollbacks only:
- Disable activation projection: the projector reports ACTIVATED for nothing (all verified-eligible items show SHIPPED with `activation_projection_disabled`) via a Nix option; or
- Keep the verifier and revert only the new request/signing tooling.
Reverting to `refactor_status.py:99-104` (`agent == "owner"`) or to the `accepted`-based ACTIVATED at `aq-pm-tracker` line 473 is not a rollback; the pre-change code is the vulnerability, and "no grants exist yet" is not a protection once the path is reachable. A tier0.d check fails any change that makes ACTIVATED reachable without `activation_verified`.
