## Blocking findings

### 1. Coordinator fallback is falsely classified as available

The backend intentionally returns `{"available": false, ...}` when coordinator status is
unavailable (`aistack.py:3242-3248`). The frontend computes
`coordinatorAvailable = Boolean(d)` (`assets/dashboard.js:5299`). That fallback object is truthy, so
the frontend assigns coordinator severity zero when it has no alert/drift. With a healthy local
payload the card can display nominal instead of unavailable.

This violates AM5's incorporated requirement that coordinator unavailability contribute unavailable
severity and that the badge be the deterministic worst of coordinator and local state. Availability
must honor the closed response signal, for example by treating `d?.available === false` as
unavailable, with a negative test for the actual backend fallback object.

### 2. The normal cache fast path extends freshness beyond both frozen limits

`get_local_direct_health()` returns the stored payload unchanged for up to two seconds
(`aistack.py:3231-3235`). It does not add elapsed monotonic time to `source_age_s`, relabel fresh data
stale after ten seconds, or erase assessed lifecycle values after sixty seconds. The refresh path
conservatively records fresh as already ten seconds old and stale as already sixty seconds old
(`aistack.py:3206-3213`), but the fast path bypasses the function that enforces those effective ages.
Consequently a fresh/healthy response can remain fresh beyond ten seconds and an assessed stale
response can retain lifecycle values beyond sixty seconds by as much as the cache TTL.

This violates the exact effective 10/60-second contract. Every return path, including the normal TTL
hit, must apply and validate effective-age projection. Add direct route-level tests at equality and
immediately above both boundaries; testing `_local_direct_cache_fallback()` alone does not cover this
branch.

### 3. Extra unbound provenance keys can be misreported as merely uninstrumented

AM5 requires any v1-shaped row carrying `local_direct` **or another extra provenance/telemetry key**
to reject the whole source. The registry adapter only recognizes a truthy `local_direct_attempted`
or a non-null `local_direct` (`aq-tui-dashboard:151-157`). A row with an attempted top-level
`producer`, `trusted`, copied provenance field, or another recognizable lifecycle-provenance key but
without those two exact keys returns `None`, which the projector reports as benign
`source_not_instrumented` rather than blocked `source_invalid`.

The adapter must deterministically distinguish records with no telemetry from records attempting
unbound telemetry/provenance and emit a rejecting snapshot for the latter. Add negative vectors for
top-level producer/trust and other frozen attempted-provenance forms, including mixed snapshots.

### 4. The single two-second child lifecycle deadline does not include cleanup

The two-second timeout context ends before exception handling (`aistack.py:3193-3203`). Timeout,
overflow, or cancellation cleanup then runs outside that deadline (`aistack.py:3217-3224`), with up
to two additional 250ms waits. The final wait timeout is suppressed, so the helper may return
without proving the owned child was reaped.

AM4, incorporated without reinterpretation by AM5, requires one monotonic two-second deadline to
cover spawn, reads, exit, and bounded cleanup, plus no live child/read task after failure. Carry one
absolute deadline into cleanup and fail closed if reaping cannot be established. Add a non-returning
terminate/kill/wait fixture that asserts the total deadline and terminal child state; the current
fake always changes `returncode` immediately and cannot prove this boundary.
