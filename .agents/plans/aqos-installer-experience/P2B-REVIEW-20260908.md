## 1. Defense in depth — PASS

`propose_selection()` has exactly one return path for a parsed model reply:
`aqos_ai_propose.py:178` — `return proposal.validate_proposal(raw, module_catalog)`.

Traced every branch of the function (`aqos_ai_propose.py:119-178`):
- HTTP/transport exception → `{"ok": False, "reason": "proposal_unavailable"}` (line 158-161), never reaches validation, never returns a selection.
- Reply not shaped like a chat completion (`KeyError`/`IndexError`/`TypeError` on `response["choices"][0]["message"]["content"]`) → same fail-closed literal (line 163-166).
- `content` not `str`/`bytes`/`bytearray` → same fail-closed literal (line 168-173).
- Any reply that reaches the bottom of the function is passed to `proposal.validate_proposal(raw, module_catalog)` (line 178) — no other function anywhere in the file constructs or returns a `{"ok": True, ...}` shape. `validate_proposal` itself (`aqos_ai_proposal.py:66-138`) never raises and only emits `ok: True` after strict JSON parse, closed-shape check, const pin, catalog-membership check, and a recursive string-content scan (Step 5, line 130) that is independent of the schema constraint.

Confirmed no other call site of `propose_selection`, `_post_chat`, or `aqos_ai_propose` exists anywhere in `scripts/` outside the test file itself (`grep -rn` over `scripts/` returned only the definition sites and the one internal call). So there is no code path in the current tree that can return a model-derived selection without passing through `validate_proposal()`.

Tried to construct a bypass: the only way to skip Step 5's recursive scan would be a `selection` payload with no string values at all reachable from `_scan_unsafe` — but `golden_profile` is required to be a string and is checked against the catalog-ID allowlist regex (`^(profile|role)\.[a-z0-9._-]+$`, max 64 chars) *before* Step 5 even runs (Step 4, `aqos_ai_proposal.py:110-114`), so an attacker also has to pass catalog membership first. Both gates are independent (catalog-membership set vs. regex/length scan) — defeating one doesn't defeat the other. No bypass found.

## 3. Fail-closed — PASS

Three independent failure classes all fail closed to the same literal `{"ok": False, "reason": "proposal_unavailable"}`, never a partial/garbage selection:
- Transport failure/timeout: `except Exception: return {"ok": False, "reason": "proposal_unavailable"}` (lines 158-161) — broad `except Exception` catches `urllib.error.*`, `TimeoutError`, `OSError`/connection-refused, socket errors.
- Malformed response shape (no `choices`/`message`/`content`): lines 163-166.
- Non-string/bytes content: lines 168-173.
- Once past those, a syntactically-valid-but-wrong-content or outright malformed-JSON reply still fails closed via `validate_proposal`'s own gates (`json_invalid`, `unknown_field`, `unknown_profile`, `unknown_role`, `unsafe_token`) — never raises, never returns a selection on any failure.

Test suite exercises timeout (`TimeoutError`), connection error (`OSError`), malformed shape (`{"unexpected": "shape"}`), and non-JSON content string — all four assert `ok: False` with the expected reason (test file lines 197-218). Confirmed by test run (below).
