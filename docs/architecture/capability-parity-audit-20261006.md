# Autonomous System Capability Parity Audit

**Decision:** the running system has healthy, useful foundations, but the available evidence does not yet establish feature parity with the ten repositories in the [curated Reddit list](https://www.reddit.com/r/SATNA_PROJECT/comments/1wvtt4c/10_opensource_repos_that_turn_an_llm_into_an/) or with Google's Always-On Memory Agent; the list is research input, not a deployed integrated stack. The archived run on **2026-10-06** recorded **214 passed, 0 failed, and 8 skipped** checks across QA0, QA1, QA6, QA7, and QA55; QA0 itself completed in **329 seconds** with 190 passes. That is strong operational evidence for the services and checks actually exercised, while much of the comparison evidence remains source, import, route-presence, or bounded unit logic. In particular, durable recall after restart, a fact-to-relationship graph loop, and live graph-assisted retrieval have not been demonstrated. The current MemoryBroker audit fact was accepted as **queued**, which is not confirmation of a durable write. This audit makes an explicit working assumption that the ambiguous Google target is the **Always-On sample**; Vertex AI Memory Bank and the Titans research architecture are distinct targets. No repository should be installed merely because it appears in the comparison.

## What the validation proves—and what it does not

The archived results are [QA0: 190/0/8](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/research_notes/Autonomous%20system%20capability%20parity/parity-qa0-live.json), [QA1: 11/0/0](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/research_notes/Autonomous%20system%20capability%20parity/parity-qa1-live.json), [QA6: 5/0/0](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/research_notes/Autonomous%20system%20capability%20parity/parity-qa6-live.json), [QA7: 4/0/0](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/research_notes/Autonomous%20system%20capability%20parity/parity-qa7-live.json), and [QA55: 4/0/0](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/research_notes/Autonomous%20system%20capability%20parity/parity-qa55-live.json). QA0 included live service, HTTP, and retrieval-smoke coverage, but it also includes static and import checks. For example, its graph-runner check validates files, syntax, handler names, route literals, and template JSON; it does not execute a workflow or inspect persisted graph state ([phase implementation](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/scripts/testing/harness_qa/phases/phase0.py:1008)). Likewise, the graph-search and graph-augmentation checks inspect source strings rather than invoke those paths ([graph-search check](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/scripts/testing/harness_qa/phases/phase0.py:3188)). A healthy endpoint or passing import therefore cannot establish behavioral parity.

The initial sandbox-telemetry lock failure was resolved under the approved QA run; Phase 0 then completed. This report makes no restart, fault-injection, configuration, or code claim beyond that archival evidence. The next QA0 graph work should test a known fact from ingest through durable storage, graph search, and a caller-visible answer.

The distinction matters most for memory. A successful fact response may only acknowledge queue admission: the state-authority contract explicitly distinguishes that stage from durable Qdrant upsert ([authority boundary](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/config/system-state-authorities.yaml:405)). The local implementation has useful temporal semantics—when a fact changes, it can close the old validity interval and query by time—but an in-process fallback does not show restart-safe durability ([superseder](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/ai-stack/mcp-servers/hybrid-coordinator/memory_superseder.py:136)). In the same way, a locally generated triple count does not show that a caller can traverse stored relationships. The 25,575 QA0 triples came from `--skip-llm` extraction without `--ingest`; the implementation returns before upload in that mode ([extractor path](/home/hyperd/Documents/NixOS-Dev-Quick-Deploy/scripts/ai/aq-index-knowledge-graph:190)). These are not defects by themselves. They delimit what is presently known: the architecture contains several of the required components, whereas the complete durable memory-and-graph behavior remains an acceptance question. The report consequently uses **partial**, **structural**, and **unproven** rather than a percentage score or a blanket “missing” label.

## Google target boundaries and the next acceptance journeys

The Google sample should not be conflated with two related but different offerings. The [Always-On Memory Agent README](https://github.com/GoogleCloudPlatform/generative-ai/blob/main/gemini/agents/always-on-memory-agent/README.md) describes a self-managed application with SQLite records and timed consolidation. [Vertex AI Memory Bank](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/memory-bank/set-up) is a managed Agent Engine capability that extracts and retrieves scoped memories with managed similarity retrieval and lifecycle controls. [Titans](https://research.google/pubs/titans-learning-to-memorize-at-test-time/) is research on a neural memory module learned at test time, rather than an external durable-memory service. Always-On parity therefore means a verified application loop; Memory Bank parity would require managed extraction/retrieval semantics and scope/lifecycle behavior; Titans parity would require model-architecture research work. The sample also accepts images, audio, video, and PDFs; equivalent multimodal ingestion and retrieval parity is currently unknown for the text-memory path. None follows from the other.

| Order | Acceptance journey | Evidence required for a decision |
|---|---|---|
| 1 | **Memory wiring, durable recall, and graph answer.** Submit a known fact, observe a confirmed durable write, restart the relevant process, retrieve it in a new session, supersede it, then retrieve the valid historical/current relationship through the graph path. | Correlated request/record identifiers, durable-store verification, restart evidence, and caller-visible graph-enriched response. This resolves the queued-versus-durable uncertainty and the QA0 graph follow-up. |
| 2 | **Workflow recovery.** Start an approval-bearing workflow, interrupt it, restart the worker, resume from the stored checkpoint, and verify idempotent final state and audit trail. | A live state record before/after restart, exactly-once side-effect evidence, and result retrieval. |
| 3 | **Behavioral evaluation with tracing.** Run representative tool/RAG journeys under versioned prompts and correlate trace, latency, failure, and scored outcome. | End-to-end trace IDs, prompt/version linkage, repeatable evaluation corpus, and outcome thresholds. |
| 4 | **Browser or sandbox only when a workload requires it.** Exercise a bounded browser task or untrusted-code task with the necessary authorization and containment. | A real workload, enforcement logs, isolation result, and cleanup outcome; project presence alone is not an adoption reason. |

These journeys turn the current source and health evidence into decision-grade parity evidence. Until then, describe the system as operationally healthy with partial, component-level equivalents rather than as fully equivalent to the external projects.
