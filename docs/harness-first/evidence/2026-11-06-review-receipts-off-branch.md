## Validation Evidence
Design.
- Store: append-only branch `review-receipts`, one file `receipts/pr<N>-<head12>.json`, schema 2: repo, pr, reviewed_head_sha, tree, base_commit, policy_version (`review-receipts/1`), run_id, reviewer_lane, author_lane, verdict, output_file, output_sha256, created_at.
- `aq-review-receipt mint --offbranch` keeps every existing check (registry row done, review role, output present and mentions the head, last `Review-Disposition:` line, reviewer differs from author) and adds the bindings. `publish` verifies the receipt again against the local registry and transcript, then writes the blob, tree and commit with a temp index and `git push <sha>:refs/heads/review-receipts`. No checkout, no index or HEAD of the working branch touched. Same content (ignoring created_at) is a no-op; a different receipt for the same PR/head is refused unless the existing one is REQUEST_CHANGES; a rejected push (non-fast-forward) refetches and rebuilds on the new tip, up to 5 times. No force push.
- Check: takes PR number, repo and head from the event, reads the current head, base and body from the API (`GITHUB_API_URL`, `GH_TOKEN`) and requires live head == event head; otherwise the run fails as stale and the run for the new head decides (a result is never reused for another head). It fetches `refs/pull/N/head` (must equal the API head), then fetches `review-receipts` and validates: repo, PR, reviewed head equals the body, tree equals the reviewed head's tree, policy version, hex formats, reviewer is not the author and matches the body, verdict matches the disposition and is not REQUEST_CHANGES. After the receipt is read it re-reads PR metadata and fails if head or body changed. All previous rejections kept.
- Fail closed: API unreadable or malformed, event head missing, stale run, PR head not fetchable or moved, branch unreachable, receipt file not a regular file, not JSON, JSON `null` or not an object, any wrong field, or PR metadata changing mid-check. Only true absence (branch or file not there) falls to migration or to "missing receipt".
- Migration: schema 1 committed receipts (body `Review-Receipt:`) validate only when no off-branch receipt exists, only for PRs numbered <= `LEGACY_MAX_PR` (720; remove the fallback once that cohort has closed), and only if the receipt's `pr` equals this PR. Schema 1 has no repo field, so legacy receipts cannot be bound to the repository; that is why the fallback is frozen. An unreadable off-branch receipt never falls through to legacy. An off-branch receipt, when present, takes precedence and must itself be valid. The receipt-only head rule is likewise legacy-cohort only.
- Merge-only updates (finding 4, pre-existing weakness): the old test (ancestry plus `git patch-id --verbatim`) ignored hunk location, so a descendant could move a reviewed edit to another identical-context hunk and pass. It is replaced: walking the first-parent chain from the head back to the reviewed head, every commit must be a merge whose second parent is an ancestor of the tip of origin's `refs/heads/main` (fetched by the run, fail closed if the fetch fails; the API's base sha is never used for ancestry) and whose tree equals the clean result of `git merge-tree --write-tree <first-parent> <second-parent>`. The PR must also target `main` of this repository: live base ref and base repo are checked at both reads, and base ref, repo and sha must be identical across the two reads (a PR retargeted to an attacker branch holding an unreviewed commit E, or a base flipped back to main between reads, fails). Conflicted, hand-edited and non-merge commits fail and need a new review (legacy cohort only: a commit that merely adds receipt JSON is also allowed). `merge-tree --write-tree` needs git >= 2.38; the local git is 2.54.0. The Actions image's git version was not verified here (ubuntu-latest ships a newer git than 2.38 as far as I know, unconfirmed); if it were older the check fails closed with a message naming the requirement rather than passing.

Tests (local bare origin, stubbed API, one real local HTTP server; no network; 52 in the check file): valid receipt with head unchanged (PR branch has no receipt commit); an edit event carrying the final head reads the live body, and a re-run on an unchanged head picks up a corrected body; an event for an old head is stale and never validates the live head; head/body changed during the check fails; unreadable off-branch receipts (fetch error, malformed, null, list, symlink) fail even with a valid legacy receipt; legacy receipts rejected past the cohort and when naming another PR; relocated-hunk commit, relocation hidden inside a merge, hand-resolved conflict, merge of a commit outside the base, and receipt-only updates past the cohort all rejected; clean automatic merge accepted; attacker-selected base throughout (retargeted branch, and forged ref=main with the attacker sha), foreign-repo base, and base flipping between reads rejected, main-throughout control passes; API down or malformed fails; live head moved or unfetchable fails; missing receipt and missing branch; malformed JSON; schema and type confusion; self-review; lane and verdict mismatch; replay onto another PR, repo, head or tree; stale head; merge-only update keeps the receipt valid; legacy committed receipt validates; off-branch takes precedence; HTTP auth path. Receipt tool: mint --offbranch + publish idempotent with working branch, HEAD and status unchanged; non-fast-forward race (a hook advances the branch mid-push, bare repo denies non-ff like GitHub) rebuilds on the new tip with nothing lost; mismatched output digest, invented/self run and schema 1 refused at publish.

## Rollback Plan
Revert the commit. Until the `review-receipts` branch exists nothing changes for PRs carrying a legacy receipt. The branch itself is inert and can be left or deleted by the owner.

## Residual Risk
This stays detection-grade (Design Decision 4). It proves: a receipt was written for this repo, PR, head and tree by a process that saw a registry row and an output file whose digest matches, naming a reviewer lane different from the author; it cannot be reused for another PR, head or tree; and the verdict is evaluated against live PR state. It does not prove who pushed it: every lane shares the owner's token, so any lane can push `review-receipts`, and CI cannot see the local registry. Receipts are as forgeable as the committed ones were (and `aq-review-receipt audit` against the local registry remains the detector). Differences from the committed form: the receipt is no longer reviewed as part of the PR diff, and branch protection on `review-receipts` (no force push, no deletion) is what makes it append-only on the server; until the owner sets it, append-only is by convention. The next step that makes review non-forgeable is a separate issuer identity (a GitHub App), which this layout allows. Accepted limits: (1) the legacy fallback has no time limit; it is removed in S3 when the landing tool switches to off-branch receipts. (2) Validation and result publication are not atomic, so a mutation after the final metadata read is possible. (3) A clean merge from trusted main can carry unreviewed semantic interactions (the limit of the merge-exemption policy). (4) Same-second push/edit ordering on GitHub is validated on the live PR, not by the tests, which use a stubbed API. Open and not fixed here: the checker runs from the PR's own checkout, so a PR can modify the checker that judges it (pre-existing trust weakness, logged by the orchestrator); a trusted copy from the base branch would be needed. Also open: check-pr-body-format still reads the event payload, so on a re-run it can show a stale result; the PR template still lists Review-Receipt as required text; mint without `--offbranch` remains the default until aq-land (S3) switches over.
